# Project Instructions — cents. (Expense Tracker)

Local-first, single-page expense tracker. No build step, no framework — plain ES modules, hand-written CSS, hash routing. Served from one Cloudflare Pages project: the static app, the five functions under `netlify/functions/` (compiled by Pages as the site's own function, through `functions/`), and a KV namespace. The reminder job runs when something calls it — the app itself on open, or an external scheduler pointed at `reminders-tick`.

## Tech Stack
- **Vanilla JS (ES modules)** — `app.js` (~9.2k lines) is the whole UI; supporting modules are `storage.js` (state persistence, validation, backup parsing, the JSON export/restore and the CSV export/import), `csv.js` (the one CSV field rule — quoting, the apostrophe guard against a note being read as a formula, and the shared row splitter and date reader — written by `storage.js`'s entries export and read back by its import, and used both ways by `tesco.js`'s workbook read/write), `settings.js` (device settings), `sync.js` (cloud sync client), `sync-merge.js` (cloud/local merge), `seed.js` (structural defaults), `profiles.js` (per-profile namespacing + admin policy), `reminders.js` (daily reminder + Web Push), `bank-import.js` (the bank statement CSV importer — a pure module reached only through `import()`), `tesco.js` (the Tesco Pay screen, roster-photo reader, pixel prep pipeline and workbook import) and `tesco-pay.js` (the pay engine `tesco.js` is built on — rates, hours, tax, week/month roll-ups).
- **`tesco-pay.js` is the boot half of Tesco Pay, and that split is load-bearing**: `app.js` imports it statically (the dashboard's Tesco line needs `monthSummary`/`shiftPay`), while `tesco.js` — 240 KB of screen, OCR and import — is reached only through `import('./tesco.js')` on the first visit to `#tesco`. `scripts/check-boot-payload.mjs` pins the static closure by name and by size, so a new eager import fails the build instead of quietly costing every boot ~240 KB of parse. The screen's own nav link warms the module on pointer-over/focus, so the tab is usually already there when clicked.
- **State**: one validated JSON document in `localStorage` (`expense-tracker:v1`), schema-versioned (`schemaVersion: 2`).
- **Cloud sync**: `netlify/functions/sync.mjs` (hosted by the function in `functions/`) keeps each profile's document in the `CENTS_KV` namespace — through `lib/store.mjs`'s documented `useBlobsModule` seam and `lib/kv-store.mjs`, so no caller changed — and mirrors it into a private GitHub repo when a token is configured, committing to KV FIRST and handing the mirror write to the request's `waitUntil` (a backup must not gate a save, and must never hold a version KV refused); `setup-token.mjs` mints single-use setup links; `lib/` holds shared auth/token/store helpers. **The endpoint is `/api/sync`** — `settings.js`'s exported `DEFAULT_SYNC_ENDPOINT`, a same-origin path served by the deployment's own function, with every sibling (`setup-token`, `reminders-push`, `reminders-tick`, `profiles-admin`) derived from it by replacing the last segment. The five are ALSO routed under their pre-rename `/.netlify/functions/*` spelling, because that is the name every device set up before the rename still has in its settings: the two spellings are the same handler, and `check-worker-config.mjs` fails if either half goes missing or if the pair stops pointing at one function. A stored legacy path, or a stored `*.netlify.app` endpoint (a host that no longer exists), is rewritten to the default by `settings.js`'s `migrateEndpoint`, so a device recovers on its own instead of reporting a network failure forever.
- **Vendors** (in `vendor/`, fetched through `loadVendor()` on first use): SweetAlert2, flatpickr, tippy/popper, Sortable, tabbable + focus-trap, Fuse.js, SheetJS — and the Tesseract OCR engine under `vendor/tesseract/`, injected on the first roster scan. (anime.js and canvas-confetti were vendored for a donut draw-in and a month-end confetti burst; both went in the slop pass, along with the files.)
- **No test framework.** Verification = `node --check` on every file + ad-hoc node scripts + live preview.

## Code Style
- Files: lowercase `kebab-case.js` / `*.mjs` for the functions under `netlify/functions/` (the directory is named for the host it came from; `functions/_router.js` hosts them now).
- DOM is built with the `$` helper (`app.js`) — it renders children as **text nodes** by default, so strings never need manual escaping. Prefer `$` over string `innerHTML`; all `innerHTML` assignments must stay constant/clear-only.
- State mutations funnel through `saveState`; destructive actions also write the **undo journal** (`saveUndoJournal` in `storage.js`) so toasts can offer Undo.

- **A route change renders and stops there.** `renderRoute` is the `hashchange` handler and all it does is call `render()`: the swap is deferred to the next animation frame (with a 24 ms timer as the guaranteed flush) and `_render` builds and appends the screen. **No view transition, no entrance animation** — and that is measured, not taste. The change used to be handed to the **View Transitions API**, which was the stutter, because a transition costs more than its animation: the browser will not run the update callback until it has captured the old state, and capturing needs a compositor frame, so a document that cannot produce one waited out the entire 250 ms fallback budget before drawing *anything* — measured at **~270 ms per tab switch (~250 of it the budget) against ~36 ms** with no transition at all, on top of the 180/220 ms cross-fade everywhere the API did work. `scripts/test-motion.mjs` pins the machinery **absent**: no `startViewTransition`, no `VT_BUDGET`, no deferral inside `renderRoute`, no rule that animates `.screen`, no `.stagger`, no `::view-transition` pseudos and no `riseIn`/`centsVt`/`countUp` keyframes — 6/6 mutations caught, so bringing any of it back fails the build. The animation-frame deferral and the crash boundary stay in `render()` — do not add a second render path. `lastRenderedRoute` outlived the transition it was written for: a route **change** scrolls to the top and takes the new screen's initial focus, a same-route repaint preserves both — it is `routeChanged` (not `entrance`) and it drives no animation. `screenIn` survives for things that appear *into* a screen already up (the bulk bar, an empty state), where a fade is information rather than latency.
- **The menu is one tap's worth of work, and its motion was the whole of the felt latency** (pinned in `scripts/test-motion.mjs`). Every row sprang in on its own (`menuRowIn`, eight `nth-child` delays ramping to 0.125s) on top of the level's slide, so measured at a phone viewport a menu open **and every drill** ran **19–21 live animations and took 285 ms** to come to rest — for rows the user had just asked to see. The rows now arrive with the panel, and the only motion left is the level's directional slide (0.12s — it is what says which way you travelled) and the trigger's burger-to-X morph (0.16s, the tap's own feedback). It settles in **160 ms with 6 animations**. `test-motion.mjs` caps every duration in that section at 0.2s and pins the per-row entrance and its stagger ABSENT (both in the CSS and in app.js, where the three `classList.add('shown')` calls went with it), so the latency cannot creep back one rule at a time. `menuRefreshLevel`'s re-render uses the same slide, which is why the Appearance toggle animates at all — it is the level arriving, not a theme flourish. The close timeouts are 160ms and are load-bearing in one direction only: they must outlast the 0.11s out-animations (removing the panel mid-animation is what makes the menu vanish instead of leave) and should not outlast them much, because the same window is how long a stale backdrop sits in the DOM if the user reopens quickly.
- **No element re-samples the page behind it** (`backdrop-filter` is pinned absent in `styles.css`). The phone edge bands were the last one: a fixed, masked strip has to re-sample its backdrop on *every scrolled frame*, for the whole length of the page, which is the trade the sticky header, the modal scrims and the dark toggle had each already lost. They then dissolved the edge with a tint plus a mask — the same path the file already documented as its no-support fallback — and the slop pass (below) removed them outright: a tinted strip is cheap, but it is still a painted band per scrolled frame plus a scroll listener and a header measurement to reveal it, and the page has no depth to dissolve any more. The one thing worth knowing about the measurement: a webview that cannot composite (the preview panel here is one) can measure *declarative* timings — durations, animation counts, what a tap arms — but cannot measure paint or compositing cost at all, which is why the menu's 285 → 160 ms is a number and the blur removal is stated as the file's own precedent rather than as a benchmark.
- **The look is flat because a later skin flattens it, not because the file was written that way — and that is a trap, not just untidiness.** The "Ledger skin" section at the end of `styles.css` overrode an earlier glass-and-gradient design instead of replacing it: `body { background-image: … }` still carried a Haikei-style turbulence-plus-radial-gradients mesh under `body, [data-theme="dark"] body { background-image: none; }`, `@keyframes btnShine` still fed a `.btn-primary::after` that was `display: none`, `.page-title` and `.logo-wordmark` still clipped a gradient into transparent text under a rule that put the ink back, and `body::before/::after`, `.card::before/::after`, `.financial-pulse::before`, `.insight-narrative::before` and `.modal::before` were five glow/blob/hairline layers that all resolved to `display: none`. The slop pass (the commit this bullet came with) cut the *losers*, so the flat values are the only declaration for each property and the vocabulary followed: `--gradient` (one solid colour) → `var(--accent)`, `--card-glass` (opaque) → `var(--card)`, `--glass-highlight` (zero alpha in light, 5 % in dark) → deleted along with the `inset 0 1px 0` glints it was written for, `--shadow-glow` (a 1 px ring) → `--ring`, `--accent-glow` → `--accent-fade`, `--ease-spring` (an overshoot) → deleted, and `--hairline-b`/`--hairline-c`, `--accent-2` and `--surface` went with their last consumers. **Renames were value-identical by construction** — `--gradient: #157A4A` *was* `--accent` in both themes — so the pass was verified as a measurement rather than by eye: 89 probe elements × 4 snapshots (390 and 1200 px, light and dark) of `getComputedStyle`, before and after, asserted equal; the only deltas the diff produced were the intended ones (the pseudo layers `→ not-generated`, three dead `transform`/`box-shadow` transitions trimmed, and the 1 px 5 %-white glint disappearing from `.bottom-tab-bar`, `.swal-popup` and `.menu-panel` — invisible in light mode, where it was zero alpha, and gone in dark). The same reasoning retired five flourishes and their reasons to exist: the month-end confetti burst (and vendored canvas-confetti), the Save button's `savePop` bounce (the disk→checkmark *swap* stays — the pop went), the Paid checkmark's `checkPop`, the donut's anime.js `stagger(90)` draw-in (and vendored anime.js: the segments are now set to their final offsets as they are built), the phone edge bands with the scroll listener, the `__hdrBottom` measurement and the resize listener that existed only to reveal them, and the dead card spotlight — a `pointermove` loop writing `--mx`/`--my` for a `.card::after` that no longer exists. `scripts/test-motion.mjs` pins all of them ABSENT (4 new assertions, 4/4 mutations caught), and the pass added **`scripts/check-css-tokens.mjs`**, which is the guard for the *class*: every `var()` read must be defined somewhere (it immediately caught a shipped `background: var(--surface)` on `.split-leg`, which had been computing to transparent for months), every `@keyframes` must be animated by something (that is `btnShine`), every animation name must exist, and `styles.css` braces must balance — the last one because the script that cut the mesh block by markers took `body`'s closing brace with it, and CSS recovers from that by parsing every following rule as part of `body`'s declaration value. Boot payload went 678 → 672 KB.

## Data Durability
Three of these are one story — the document is the whole of the user's data — and the fourth is the reason it can be written down again at all.
- **A backup can be read back, not just written.** `Export data` had no counterpart anywhere in the app (no `FileReader`, no file input outside the Tesco importers), so the backup the quota notice tells the user to make could never be opened. `Data → Restore from backup` reads a `.json` export and **merges** it (`mergeStates`, the same union the cloud path uses): the newest version of each entry wins, tombstones still hold, and nothing on the device is deleted. `parseBackup(text)` in `storage.js` owns the rules — pure, never throws, and answers with a reason the UI words for the user (`empty` / `too-large` / `unreadable` / `not-a-backup`) plus `kept`/`dropped` counts, because a file whose entries were all junk validates to an empty document and a merge of nothing looks like a successful restore of nothing. Two things are stripped before validation and both matter: **`settings.pinHash`** (validateState MIGRATES a legacy hash into device storage when the device has no PIN, so an untrusted file would otherwise get to set this device's lock — the app's own export deletes the key, so a real backup is unaffected) and **`localResetAt`** (a whole-document tombstone that later data superseded; restoring an old copy of one would re-assert it). Both caps — 32 MB of text, 100k entries — are checked *before* the parse, so an absurd file is refused for its size rather than reported as unreadable. Pinned in `scripts/test-integrity.mjs` (“the other half of a backup: reading it back”, 10/10 mutations caught).
- **A restore is one undo step, and it reverts the whole document.** The undo closure snapshots `state` before the merge and writes it back wholesale — a merge touches settings and the Tesco tables too, so the entry-only journal is the wrong shape for it. It is therefore session-scoped, and `trackAction` with no journal data clears the reload-safe journal on purpose: that journal describes a different action.
- **The quarantine copy is reachable.** `loadState` parks a document it cannot parse instead of dropping it; the notice named a storage *key* at a user with no way to open one, and `unreadableBackup()` was exported but imported by nobody. `Data → Recover unreadable copy` appears only when such a copy exists, offers it as a merge when it parses at all, and offers the raw bytes as a download when it does not — those bytes are the only copy of that ledger.
- **A second tab is a second copy of the document, and it used to clobber.** Every tab holds the whole document in memory and every save writes ALL of it back, so the tab that writes second erases the entry the other one just added; there was no `storage` listener and no `BroadcastChannel` anywhere. Now a foreign write is merged: the tab that still holds something the writer did not writes the union back. `foreignWriteNeeded(merged, incoming)` (in `storage.js`, pure and pinned) is what stops the pair writing at each other forever — after one round trip neither side holds anything the other lacks, so nobody writes again. The document is re-read from storage rather than taken from `ev.newValue` (an event is a notification, not a snapshot, and `newValue` is null when a key is removed). Verified live with two tabs: a stale write that dropped the other tab's entry came back as the union, with zero further writes from either side.
- **The ledger is also a spreadsheet.** `Data → Export CSV` writes one row per entry (`entriesCsv` in `storage.js`, `ENTRIES_CSV_HEADER`: date, type, category, details, amount, method, note) — newest first with the History screen's own tie-breaks, the label rather than the stored id, and money at two decimals because "12.40" has to stay a cell a spreadsheet can total. The **label resolvers are handed in from `app.js`** (`categoryLabel`/`methodLabel`) instead of being re-derived in `storage.js`: a second copy of the naming rules is a second answer to "what is category `gro` called", free to drift from the one on screen — and custom categories live in the document's own `settings`. **The file reads back too**: `Data → Import CSV` (`openCsvPicker` → `parseEntriesCsv` in `storage.js`) matches the header **by name** (case- and whitespace-insensitive, reorderable — a spreadsheet rewrites columns without asking), resolves each label **back** to an id through the resolvers `app.js` hands in (`csvCategoryId`/`csvMethodId`, the mirror of the export pair, against the document's own tables), and — because the file carries **no ids** — skips any row identical to one already in the ledger, multiset-wise (importing the same file twice must not double the ledger, and two identical coffees on one day still import both when neither is here). Refusals are reason-worded like `parseBackup`'s (`CSV_REFUSAL`), amounts are never silently rounded or stripped (`''` must not become 0, `€12.40` is dropped rather than cleaned), and the merge is `applyRestore`'s whole-document undo — one step, cancellable. A transfer or split exports **without** its pairing column, so legs come back independent (validateState turns a lone transfer leg into an ordinary expense — visible spending, never a phantom pair); the CSV is a flat table and pretends to be one. The field rule lives in **`csv.js`**, shared with `tesco.js` (which writes the workbook out and reads it back), because a rule with two implementations can disagree with itself: quoting when it has to, and an **apostrophe in front of a value a spreadsheet would read as a formula** — a note can be typed, imported from someone else's file, or arrive in a synced cloud copy, so the export is not a safe container for one. A plain number is deliberately excluded from that guard, or the apostrophe that defuses `=SUM(A1)` would turn a −56.08 refund into text. The UTF-8 BOM is added at the file boundary only (Excel on Windows reads a BOM-less UTF-8 file in the machine's ANSI code page), so the text the tests compare is what `csvDocument()` produced. **The field rule is total, and its escape is lossless** — both were counterexamples the fit-all audit measured rather than features anyone had stated. `csvRows(null)`/`csvRows(undefined)` answer no rows (every reader in the file coerce the same way — csvCell, csvUnquote, csvDate, isRealDate), `entriesCsv(state, labels)` holds a labels argument that is not a table to the same rule it already held a hostile `state` to, and `suggestBankMapping` answers "nothing looks like that field" (all `-1`s) for a column list or row list it cannot read — a throw in any of them is a screen that never draws, and the bank mapper's screen is the one moment a user could fix the file by hand. And the apostrophe guard needed escaping itself: a value that BEGINS with an apostrophe and reads as a formula after it (`'=x`) came back as `=x`, because the reader took the user's own apostrophe for the guard and stripped it — an export/import quietly editing a note the user typed (measured: `csvUnquote(csvCell("'=x")) === '=x'`). `csvCell` now doubles that apostrophe and `csvUnquote` strips exactly one, both asking the same predicate (`CSV_GUARDED`), so the rule is its own inverse: `'=x` → `''=x` → `'=x`, while `'hello` and a text-flagged `'12.40` are untouched and `-56.08` is still a number. Pinned beside the other CSV checks in section 5.
- **One answer to "is this a date", and one shape for the document — the two rules the fit-all audit found with more than one.**
  - A day of the right SHAPE but not on any calendar passed every check the app had. `Date.parse('2026-02-31')` answers a finite timestamp for 3 March — `Date.UTC` ROLLS the day over — so "it parses" was never the question, and a workbook cell reading `31/02/2026` arrived as a shift dated the 31st of February: drawn on a card, grouped by `weekStartOf` into the week of the 3rd. Measured before: `csvDate('2026-02-31') === '2026-02-31'`, and the same for `'2026-13-01'`, `'2026-00-10'`, `'2026-04-31'` and a day-first `'31/02/2026'`. The rule is a **round trip** and it lives in `csv.js`: `isRealDate(value)` parses `YYYY-MM-DDT00:00:00Z`, reads the day back out and compares it to what was written — the one form of the check a rollover cannot pass. It is the only copy: `csvDate` (every form a cell arrives in — ISO, an Excel serial, a sheet's own day-first locale) routes every parsed form through it, `isValidCheckpointDate` in storage.js **delegates** to it (entries, checkpoints, recurring bills and both Tesco tables; `TESCO_DATE_RE` and `CHECKPOINT_DATE_RE` are gone), and `dateOk` in tesco-pay.js is one line calling it. So a first session ran on a document its own validator would have rewritten, and the stored shape changed by itself on the second load — `validateState` was **not idempotent** (measured: 8 settings keys on the junk path, 16 on a validated document). Every reader guards with `|| []`/`|| {}`, so nothing broke, which is exactly why this kind of drift survives: it is invisible until a new reader assumes the key. Closed at the source instead of at every reader — `defaultState()` **is** `validateState(...)`, so there is one shape and the default is it. Pinned in `scripts/test-integrity.mjs` **section 2b** ("one shape, and days that exist"): junk input and a validated document must have the SAME settings shape, `validateState` must be idempotent on both paths, the fresh document must survive its own save/load round trip byte-for-byte, and a Tesco row dated the 31st of February must vanish rather than move; `dateOk`'s six values are pinned in `scripts/test-tesco.mjs`. **17/17 mutations caught** across the two guards (including reverting `csvDate`'s round trip, `isValidCheckpointDate`'s delegation, `dateOk`, the default document and both totality guards), verified live in the served app: a fresh install boots on a 16-key document with the getting-started card, `Payment methods` and the Add screen read the empty tables without a throw, and a workbook cell dated `31/02/2026` is refused.

- **A bank statement is the app's second writer, and here the header is a guess.** ☰ → Data → **Import bank statement** loads `bank-import.js` through `import()` — pure top level, no DOM, so `scripts/test-integrity.mjs` **section 17** reads it behaviourally the way section 15 reads `lidl.js`. The app's own CSV round-trip works because both ends agreed on the header; a bank agrees on nothing (AIB `Date, Description, Amount (eur)`, Revolut `Completed Date, Description, Amount, Currency`, half of them a Debit/Credit pair instead of one signed column), so `suggestBankMapping` guesses, the guess is shown on one mapping screen before anything is written, and the pair-vs-signed-column case is chosen through toggle buttons rather than inferred. Four rules carry over: **never round** (an amount not exact to 2dp is counted and its row skipped, never tidied — `bankAmount` reads `€1,234.56`, `1 234,56`, `(12.40)`, `12.40 DR` and answers null for prose like `closing balance`, so a balance column cannot become money by landing in the amount position); **never guess a date** (`bankDate` is day-first for an Irish bank, reads month names both ways and returns null rather than swapping an ambiguous one); **re-import adds nothing** (rows match the ledger multiset-wise on date|direction|description|amount|account — the file carries no ids, so idempotence is the only defence, while two genuinely identical coffees in one file still both land); and **the category comes from the app's own table** — `categoryFromDescription` in `app.js` is handed in, and is the same function `parseReceiptLine` now calls, because a second keyword table is a second answer to "what is a Tesco shop". The wiring is source-pinned at the end of section 17 (the menu row, the ctx — `existingEntries`, `guessCategory`, `commitAdded` — and the file input's `.bank-import-file` class beside `.restore-file`: a hidden input a test cannot find is one nobody can drive), the module sits in `sw.js`'s `SHELL` so a first offline visit can import it, and it is declared in the a11y harness's `MODAL_OPENERS` with its own audit step.
- **Durable storage is asked for once per boot** (`navigator.storage.persist()`, a no-op once granted) and the Data menu shows the document's own size and whether the browser promised to keep it (`persistent` / `best-effort`) — the ledger is the whole of the app's data, so “best-effort” is a fact the user should be able to see. The call is refused in some profiles; the readout says so rather than pretending.
- **The GitHub mirror can fall behind in silence, so it is now measured after every save and written down where the user will see it.** A save commits to the KV record and hands the mirror write to `waitUntil`; its failure is logged and never returned, because a code host having a bad day must not fail somebody's save (see the Cloud sync bullet above). That is the right trade for the save and the wrong one for the backup: the record can hold a version the repo does not, and the first person to find out was whoever restored from the mirror. `lib/cloud.mjs` therefore ends every save with **the gap check** — `checkMirror` reads the blob back over the Contents API and compares its hash with the record's own version token — and records the verdict (`{ state, checkedAt, recordVersion, mirrorVersion, commit, wrote }`) in the KV record beside the document. **The read-back is the point, not a formality**: the mirror write's own answer says what the writer believed it sent, and only a comparison catches a blob that another device (or a force-push, or a hand edit) owns — the stubbed GitHub in `test-cloud.mjs` grows an `overwrite` hook precisely so that case is a test rather than a claim. The vocabulary is closed and classified by a **pure** `classifyMirror` (`in_sync` / `pending` / `behind` / `diverged` / `missing` / `unverifiable` / `no_document` / `unconfigured`), where `behind` and `diverged` are told apart by whether that save's write landed, and **`pending` exists because a save answers before its mirror write** — an on-demand check taken a second later must not call the in-flight window a gap, and where nothing has been claimed about a version, nothing is denied either. `sync.mjs` exposes it in three shapes: a plain GET rides the recorded verdict along with the document it already fetched (a read that measured would make every 30 s poll cost a GitHub round trip), `PUT` returns it when the host reached one before answering (null on a real deployment = “not measured yet”, never “in sync”), and **`GET ?mirror=1`** compares now and answers with the verdict alone — no document — which is what the Data menu asks for on open. On the client `sync.js` owns the wording (`mirrorStatus`, with `gap` as the only thing that colours anything: `behind`/`diverged`/`missing`/`unverifiable`), `settings.js` caches the verdict at a bounded size, and `app.js` says it out loud twice — a toast on the transition into or out of a gap (once per transition, never per poll) and the Data menu's own line, which re-checks live so it cannot be a verdict from days ago and asks once more when the answer is `pending`. Pinned in `scripts/test-cloud.mjs` (the vocabulary, `in_sync` recorded with the save, the free read, the on-demand check's shape, `behind`, `diverged` via `overwrite`, `missing`, `pending`, `unverifiable`, `no_document`, `unconfigured`, and that the mirror's update is still one PUT that comes *first*) and in `scripts/test-sync.mjs` (the vocabulary from both ends, the client's URL, and that a reply which is not a verdict is never a pass).
- **A payment method the user owns, and the one rule that makes removing one safe.** **☰ → Payment methods** (`openMethodManager` in `app.js`) lists every method a picker offers next to the ones the user added — `settings.customMethods`, unioned by id like `customCategories` — and lets them be added, removed and restored. Two rules carry the whole feature, and both exist because the obvious implementation silently eats the ledger. **A method removed from the pickers stays a VALID method id** (`updateAllowedMethods` in `storage.js`, the twin of `updateAllowedCategories`, called before any entry is validated): `validateEntry` DROPS an entry whose method it does not know, so removing an id from the allowed set would delete that entry's entire history at the next load — a deletion that never appears as one. And **removing is a flag, never a removal from `customMethods`** (`settings.methodHidden: { [id]: boolean }`), for two reasons: the entry that used it must keep resolving its label (`everyMethod()` → `methodById()` → `methodLabel()`), and a deletion from the list itself would be refilled by the cloud merge, which unions that list by id. The **`false` is a value, not an absent key**, and that is the subtle half: the settings merge is a per-key spread (`{...older, ...newer}`), which can overwrite a key but never delete one — so a Restore written as a deletion could never beat the other device's `true` and the method would come back hidden on every sync, forever. `mergeStates` therefore unions `customMethods` and takes `methodHidden` per key from the fresher side, in both directions (pinned: a removal on the older device survives, a restore on the fresher one wins). Only the **built-ins** are protected from deletion — `AIB`/`Revolut`/`RS` key the Balances rows, the checkpoint series and the account math, `TG`/`LG`/`AG` the gift-card totals, `RS` the budget filter — so they get **Hide** where a custom method gets **Delete**, and either one only leaves the pickers. In the UI the three resolvers are `everyMethod()` (the document's whole catalogue, for labels and validation), `allMethods()` (what a picker offers) and `methodPickerIds(selected, base)` (what a picker offers **for an existing record**), and the last one is not a convenience: `formView`'s method select RESETS its value to the first option when the current one is not in the list, so an entry edited after its method was removed would have been silently moved to another account on Save — the shared form therefore asks for `methodPickerIds(data.method, methodOpts())` whenever it holds an `initial` (the Edit sheet) and only offers `allMethods()` for a new one. Adding a method through the manager writes `false` for any stale flag on its own slug, so a name just typed is offered immediately rather than being blocked by a tombstone from another device. The manager is an a11y-audited surface (it had to be declared in the harness's `MODAL_OPENERS`, which `check-a11y.mjs` asserts in both directions — 5 menu levels, 7 menu modals, 21 surfaces), and the rules above are pinned in `scripts/test-integrity.mjs` (section 12, “a payment method the user owns”): the four data rules run through `validateState`/`mergeStates`, and the three that only exist in `app.js` — which cannot be imported in Node, since it touches the DOM on evaluation — are pinned against its source text the way `test-motion.mjs` pins `paintFigure`. 11/11 mutations caught, and the first draft of the restore check is why the `false` exists at all: asserting that a restore survives a merge is what proved the key-deletion version could not.

## Deploys Reach the Device
Four independent things have to hold for a change to actually land on a phone that already has the app, and `scripts/check-freshness.mjs` pins all four.
- **Every app asset revalidates.** Each file the app loads (`.js`, `.css`, `.html`, `.json`, `.png`, `.woff2`, `.wasm`, `.gz`) and the root path `/` is matched by a `_headers` rule that sets `no-cache, must-revalidate`. A path with no such rule inherits the platform default instead, which is invisible in the repo and invisible locally — no such header is ever sent by the dev server — so the guard walks the checkout and fails for any shipped asset without one. `/*.js` and `/*.css` are Cloudflare *header* globs and a mid-path `*` there spans slashes — verified against a deployed site, where `/*.png` answers for `/icons/icon-192.png`. That is the same globbing the `for =` patterns relied on, which is why every header rule ported across unchanged.
- **The worker is network-first, and never serves the previous deploy to an online user.** `respondWith(fetch(…, { cache: 'no-store' }) → cache → offline fallback)`; the `no-store` is load-bearing twice over, because the browser's own HTTP cache would otherwise answer before the network even with a revalidating header.
- **The worker script itself is never taken from cache** — `register('/sw.js', { updateViaCache: 'none' })` in `index.html`, or Chrome honours its own cached copy for up to 24 hours and the new cache namespace and shell warm arrive a day late.
- **The build baseline outlives the worker, and this is the one that actually bit.** "A redeploy reaches the device" rests on the worker diffing the navigation document it just fetched against the one it saw last and telling the open tabs. That baseline was a `Map` in the worker's own scope — and a service worker is torn down after ~30 seconds idle, so by the time a phone has been in a pocket for a few days the worker that saw the previous build was gone. The next check therefore looked like a **first sighting**, and the first sighting is recorded silently on purpose, so the ONE case the machinery exists for (a PWA that has not navigated since the deploy) stored the new build, told nobody, and kept showing the old one until it was killed by hand. It now lives in Cache Storage under its own un-versioned key (`cents-build`, which `activate` deliberately does not sweep — unlike the shell cache, its job is to survive the deploy that changed the shell), and it is **read fresh on every comparison rather than mirrored**, because two sources of truth for this is a race waiting to happen. Two smaller holes were closed beside it: the diff reads a **clone taken in the same tick** as the response (a clone taken after the page has consumed it throws "body already used" and the notification is lost without a word), and both entry points — a navigation, and a tab asking on refocus — go through the one comparison. Verified end-to-end on the served app by simulating a deploy: overwriting the stored baseline made the next refocus check broadcast `centsNewBuild`; a second check with no change stayed silent, so the fix cannot become a reload loop. The guard pins the baseline's home, both read and write, both entry-point shapes, `activate` keeping the cache, and the same-tick clone — 8/8 mutations caught, including putting the `Map` back.
- **Not covered, and worth knowing:** the baseline is per *device*, not per client. If a second tab missed the broadcast that a navigation fires, its own later check compares against the already-advanced baseline and stays quiet — it is corrected on its next navigation. The single-tab/PWA case, which is the one that fails visibly, is what this fixes.

## Installed Like an App
What makes an installed copy behave like an app rather than a web page in a window. None of it needs a packaged app store submission, and every item fails **silently** — which is why `scripts/check-app-shell.mjs` (81 assertions, 25/25 mutations caught) pins the lot, half of it against `app.js`'s source text because a Node guard cannot run the DOM.
- **Android's back gesture closes the top sheet.** Every sheet is a `.modal-bg` (nineteen call sites) or the menu's `.menu-backdrop`, each owning its own `close()`. Rather than thread a history hook through twenty call sites, ONE `MutationObserver` in `wireBackGesture()` watches `<body>` for a sheet appearing (the same shape as `wireModalFocusTrap`, installed at boot for the same reason), pushes a history entry for it, and a `popstate` closes the top one through **the convention every sheet already has** — Escape, which each modal guards with `isTopModal`, with a click on the backdrop as the fallback. So back does exactly what Escape does and cannot drift from it. Four rules: the **lock is never closable** (`.pin-lock-bg` is a `.modal-bg` like any other, so this is a security hole dressed as a convenience); **onboarding is exempt** (a stray press must not walk the user out of a half-filled first run — it has a visible Skip); a sheet can opt out with **`data-no-back`**, which pushes no entry at all so back keeps its old meaning (the profile picker does when `!cancellable`); and a sheet that closes **itself** gives its entry back only while that entry is still on top, checked on a later task — the deferral is the point, because the menu's own rows close it *and* navigate, so by then the browser has pushed the navigation entry and popping would undo the navigation the user just asked for. The known limit: an entry left under such a navigation is still on the stack, so the first back press is spent dismissing it (popping to a URL that is already current, so nothing visible happens) and the second leaves the app. Counting the call, not the name, matters here: `test-ui-libs`'s "installed once, at boot" assertion counted the *string* `wireModalFocusTrap()` and broke the moment this block cited it as the pattern to follow — it counts the boot **call** now.
- **A line shared into the app becomes an entry, and is never saved for you.** `manifest.json` registers a `share_target`, so another app's Share → cents. arrives as `?title=…&text=…&url=…` **ahead of** the `#add` fragment the target names — which is why `readSharedText()` reads `location.search` and not the hash every other part of this app uses. The text is put in the **Quick entry**, not stored: it is whatever the other app chose to send ("€18.50 at Tesco 12/09") and the parser plus its live preview is what turns it into something the user can read and confirm. It is consumed **once, in `screenAdd`**, because the app may still be locked when the share lands — the screen does not exist until it is unlocked — and the query is dropped from the address on the way in, so a reload cannot prefill it twice. GET rather than POST deliberately: a POST with files would need the service worker to intercept it, and the worker is the one file whose correctness this project guards most carefully.
- **The manifest is the install surface, and it is complete.** `id`/`scope`/`start_url` are all `/` (without `id`, a browser derives one and can install a *second* copy the day the start URL changes; without `scope`, every URL is in-scope, which is how a navigation ends up in a tab with a URL bar). `orientation: portrait` is a call, not a default — the layout is designed vertically and an installed copy that rotates mid-entry is the one state nobody watches on a phone — and it is one word in the manifest to change. `shortcuts` gives launcher long-press entries, and each URL is checked against **`seed.js`'s own `TABS`** rather than a copy of that list, because a renamed route leaves a dead launcher entry that no app code would ever notice. `screenshots` carries the one real capture in the repo (`screenshots/dashboard-desktop.png`, `form_factor: wide`) — a **narrow** phone capture is what a store listing wants, and there is deliberately no entry claiming to be one. The guard also opens every icon and screenshot and compares the declared `sizes` with what the **PNG header** actually says, because a `sizes` that lies is accepted everywhere and looks wrong only on a launcher.
- **The app's name is one string, and the document title starts with it.** An installed window's title bar is composed by the browser, not by the app: Chromium's `WebAppBrowserController::GetTitle` shows `"<app name> - <page title>"` unless the page title already starts with the app name, in which case it shows the page title alone. So `manifest.json`'s `name` and `index.html`'s `<title>` are one decision and not two — the day the manifest was renamed to `cents. — expense tracker` while the document still read `cents. - personal expense tracker`, an installed window printed **both**: `cents. — expense tracker - cents. - personal expense tracker` (a hyphen is not an em dash, so the prefix test failed and the name was prepended). The title is now the manifest's name byte for byte, and the guard asserts `startsWith` against **both** the `name` and the `short_name`, because which of the two a given Chrome composes with is not worth betting on — a tagline that keeps the name in front of it reads once either way, and is what a future rename should use. `short_name` and `apple-mobile-web-app-title` stay the bare `cents.` (a launcher label and an iOS home-screen label, both of which truncate), and the guard holds those two equal to each other as well.
- **No web-page tells on a touch screen.** `overscroll-behavior: none` on `html, body` — not on the scroll containers — turns off overscroll *chaining* only: no Chrome pull-to-refresh reloading the app mid-scroll at the top of a screen, and no two-finger back-swipe racing the cards' own swipe-to-dismiss. In-page scrolling, rubber-banding inside a sheet and every touch handler are untouched. (The rest of the touch feel was already there: `-webkit-tap-highlight-color`, `touch-action: manipulation`, `user-select: none` on the chrome, `100dvh`, `viewport-fit=cover`, `interactive-widget=resizes-content`.)
- **`/.well-known/` is the one dot-directory a CDN does serve**, and `check-freshness.mjs` said the opposite in a comment while skipping every dot-entry in its walk. Digital Asset Links can live nowhere else, so it is walked like any other directory now — meaning a file dropped in there is held to a content type and a revalidating cache rather than to the platform default. The rule exists before the file does, so adding an installable app package later is one file, not also a config change. An unverified package opens as a plain browser tab **with a URL bar**, which reads as a bug rather than a missing file.

## The First Screen (the end-user pass)
What a fresh install is told and what the early dashboard claims — an end-user pass over the whole app, pinned in `scripts/test-integrity.mjs` **section 18** ("what a fresh install is told (the end-user pass)"), source pins against `app.js` because `app.js` cannot be imported in Node.

## Accessibility
- **The audit is a page, and a Node guard keeps it honest.** A Node script cannot read a rendered DOM, so the sweep lives in `a11y-harness.html`: it loads the real app in a **visible**, CSS-scaled iframe and drives it through every route and every surface that *opens* — the menu and its drill-downs, and the modals they reach — never clicking inside an open modal, so the ledger it audits is untouched. The frame must stay on-screen (the app defers its render to an animation frame and a background frame is throttled, so a hidden harness audits nothing) and **every step gets a fresh frame reload**, because a modal left behind is a second scope counted against an unrelated surface. It reports four defects per surface: a control with no accessible name, two controls in one scope sharing an `aria-label`, a form field with no label at all, and an `<img>` with no `alt`. Its verdict is deliberately the **sum of all four**.
- **The audit has to run in a state a user can be in, and it must never write the ledger.** A first run covers the whole viewport with the setup overlay, and nothing in the menu is reachable behind it — so a run that drives the menu anyway audits screens no user can reach, and the overlay's own PIN fields then count as duplicates of the menu's (that is exactly how a fresh device reported "New PIN ×2"). The harness therefore walks the overlay out through **its own skip control** before auditing, folds the outcome into a run-level note (`setup overlay dismissed` / `no setup overlay`, and a stuck overlay makes the run non-clean), and reports what each skipped surface needed. It must never seed storage to get there: it is served from the app's **own origin**, so it shares the app's `localStorage` and a seeded document would overwrite the ledger the harness promises not to change. Both rules are pinned in `scripts/check-a11y.mjs` (as call sites, not names) and proved by 8/8 mutations.
- **`aria-label` is an addressed identity, not a label** — `restoreFocusedField` looks fields up by it and so does the harness, so two controls on one screen sharing one is a bug rather than a cosmetic wart. That is why the edit sheet's fields are `Edit shift …` while the Add-shift card owns `Shift …`.
- **`scripts/check-a11y.mjs` pins the harness against the app's own lists**, so the audit cannot quietly stop covering the app and report 0 problems for the part it skipped: every route in `seed.js`'s `TABS`, every level `menuDrill()` can reach, and every modal `buildMenuLevel()` opens — declared in the harness as `MODAL_OPENERS` and asserted **both ways**, so a stale claim fails as loudly as a missing one (5 menu levels, 8 menu modals, 22 surfaces today — the bank statement import is the eighth). Exactly three openers are exempt, and each is stated in the guard rather than assumed: `openRestorePicker` (the OS file dialog, which a page cannot see or dismiss), its CSV twin `openCsvPicker` (same dialog, accept list swapped), and `showProfilePicker` (the menu row and header chip that reach it exist only on a device with more than one profile, so a step would report “skipped” on every ordinary run — a skip has to mean “this device could not reach it”, not “this device never has it”). It also fails if the verdict stops counting any of the four defect classes, if the page stops being dev-only (`.assetsignore` must list it — on this host that means it is never uploaded at all, the one mechanism that replaced a 404 rule plus an ignore entry), or if the harness stops being named in README/CLAUDE — an audit nobody knows about is one nobody runs.
- **The one defect that actually shipped is pinned statically**: the History month chevrons were `monthNav(iconSpan('chevron-left'…), …)` with no label, and an icon span is `aria-hidden`, so they read as "button, dimmed" and nothing else. `monthNav(label, onClick, disabled, ariaLabel)` is what writes the label, and the guard fails any call whose visible label is an `iconSpan(` and which passes no fourth argument.

## Vendored UI Libraries
The vendored browser builds — eleven minified ones, one stylesheet (`flatpickr.min.css`) and the Tesseract OCR engine in `vendor/tesseract/` — live in `vendor/` and are fetched through the one lazy loader (`loadVendor(name, { js, css })` in `app.js`), because CSP `script-src 'self'` forbids a CDN and there is no bundler. Each degrades gracefully when its file is missing, and `scripts/test-ui-libs.mjs` pins that they do what the app assumes.
- **SweetAlert2** — the themed `confirm()`/`swalConfirm`, falls back to native `confirm()`.
- **flatpickr** — date fields; the native `<input type="date">` works meanwhile.
- **tippy/popper** — chart popups (`wireChartTips`); popper must load before tippy.
- **Sortable** — drag-reorder lists.
- **tabbable + focus-trap** — modal focus containment. **Order is not cosmetic**: focus-trap 8.2.2's UMD calls `t(a, e.tabbable)` and does not bundle tabbable, so tabbable must load first (`app.js`'s `syncModalFocusTrap`). `escapeDeactivates: false` keeps Escape the modal's own business — Escape does not deactivate the trap.
- **Fuse.js 6.6.2** — History search. Stay on 6.x: **7.x publishes only `.mjs`/`.cjs`, no UMD**, so it cannot be vendored. `threshold: 0.3` is measured, not chosen by feel — at 0.4 `"12.40"` also matches a €61.50 row. `ignoreLocation`, `minMatchCharLength: 2`, weights details .5 / note .25 / categoryLabel .12 / methodLabel .08 / amountText .05. A transposed word (`trian`) is not matched at any threshold.
- **SheetJS `xlsx.mini.min.js` 0.18.5** — the Tesco workbook import. It is the **mini** build: no writers, no codepage tables, no legacy `.xls` reader, which is why the accept list omits `.xls`. Dates arrive as Excel serials, not `Date`s.

## Conventions
- Commits: concise imperative summaries ("Fix …", "Add …", "Exclude … from …"), no conventional-commit prefixes, pushed straight to `main`.
- Amounts are euros as numbers validated to 2dp (`Math.round(a*100)/100 === a`); never silently round imported money.
- Budget calculations exclude load/withdraw balance adjustments and Revolut Savings (`RS`) transactions — check existing filters before touching budget math.
- Setup links carry encrypted tokens; the endpoint whitelist + post-unlock confirm dialog are security invariants — never bypass them.
- **Never touch the user's profile data.** Earlier updates deleted a user's profile once, so the profile record (`cents:profiles`), the profile-namespaced keys (`cents:p/<id>/*`), `profiles.js` and its admin policy are read-only unless the user explicitly asks for a profile change: no code path may `removeItem`/reset/migrate them, no test may write to them (probe read-only, or exercise the logic in Node against fixtures — a snapshot-and-restore in live preview is not good enough), and a change that must reshape profile storage needs the user's explicit instruction first.
- **Lidl receipts reach the ledger by themselves — and the rules that make an automatic writer safe (the TRY).** `lidl.js` runs once per page open (the moment the app is accessible, after the PIN) and from ☰ → Data → **Pull Lidl receipts**; it reads a LOCAL relay (`python lidl-spike.py serve [--mock]`, because Lidl's API sends no CORS headers — measured: OPTIONS → 405) which keeps the refresh token on the machine and hands the page only normalized receipts. One receipt becomes ONE `expense` entry on `LG` (the Lidl gift card), so the ledger and the card balance move together — `balanceDelta` counts an expense on a gift-card method as money leaving the card. **The relay is probed only from a page that can answer it** (`relayReachable()`, the gate in front of `/status`): the relay listens on the loopback of the machine the BROWSER runs on, so the page has to be served from that machine — a loopback hostname (`localhost`/`127.0.0.1`/`[::1]`/`*.localhost`/`*.local`) or any plain-http page, which is how this app is developed and how `lidl-spike.py serve` is documented to be used. Before the gate, every open of the deployed site asked every visitor's DEVICE a question no device could answer: a console error per page load (measured: one `ERR_FAILED` in the served app), a request Chrome's Local Network Access rules treat as something to gate on a public page, and on a phone a probe of the phone's own 127.0.0.1. The automatic pull is silent about the skip; a manual tap still gets the relay's sentence ("The Lidl relay runs on the machine you use it from - open cents. there to pull receipts."). Three rules, each a way an automatic writer could corrupt the ledger, pinned **behaviourally** (lidl.js imports clean in Node; its top level is pure for exactly that) in `scripts/test-integrity.mjs` section 15: a **bounded window** (`LIDL_WINDOW_DAYS` back, up to today — never all history; an absent relay reads as “pull nothing”), **never-resurrect** (a ticket whose mark points at an entry the user deleted is never written again; the user's own identical line wins instead), and **never-round** (an amount not exact to 2dp is dropped). It commits through `commitAdded`, hoisted to module scope for this, so the ONE duplicate gate, the undo slot and the tombstones cover the automatic writer as they cover a hand entry — app.js's wiring (module scope, unlock gate, the row handing `commit: commitAdded`, no static import) is source-pinned beside the behavioural set. **11/11 mutations caught**; live-verified against the mock relay end to end: pull on open, −€58.15 on the card, reload silent, a deleted receipt stayed deleted, and the manual row reports its skip reasons (`No new Lidl receipts (1 window, 1 imported, 1 deleted).`).
- **There is no Tesco gift-card balance automation, and building one again is a dead end.** Measured: the card ledger is **Blackhawk Network's** stored-value platform — an iframe on a *different origin* (`https://wbiprod.storedvalue.com/wbir/clients/tesco`) behind a reCAPTCHA v2 — while `tescogiftcards.com/api/v1` is the **shop**, not the ledger. Its captcha-free `POST /api/v1/validations/stored_card` answers `{"errors":{"stored_card_number":"not found"}}` for a real card *and* for a second one supplied as a control, and `POST /api/v1/balance` returns `400 {"error":"Invalid Captcha response"}` *before* it reads the card. No public API exists: GitHub search for the host returns nothing, Blackhawk's developer portal is merchant-only, and the one third-party checker that handles Blackhawk pays Anti-CAPTCHA to solve the challenge — which this project bars, and paying a vendor does not change what is being defeated. The feature and its spike were therefore deleted outright (a relay, then a row that opened Tesco's page, then nothing), with `scripts/test-integrity.mjs` section 16 pinning the absence so it cannot creep back. To check a card: Tesco's own balance page where a human solves one image challenge, the phone line, the in-store Customer Service Desk, or the balance printed on the till receipt.
- Tesco Pay's **Quick entry** card is a thin wrapper around two module-scope, harness-pinned functions in `tesco.js`: `parseShiftText` reads the line, `shiftPreviewLine` renders what will be stored. Add a case to `scripts/test-tesco.mjs` rather than checking the card by eye — a mis-read line is a mis-paid week.
- Editing a stored shift goes through the same pair of module-scope, harness-pinned pieces: `applyShiftEdit` owns the rules (the importer's own — a date, or clock times, or stated hours) and returns `{ ok, shift }` or `{ ok, field, error }`; `updateShift` in `screenTesco` commits its answer through `snapshot`/`commitTesco` so an edit is one undo step and re-sorts the row into the week its new date belongs to. The row keeps its `id` (sync unions by id) and its `createdAt`. Add rules to `applyShiftEdit` + `scripts/test-tesco.mjs`, not to the sheet.
- A booked **week off** is not a shift but a row that states hours and no clock times — the sheet's own shape, and what the Quick entry already wrote for `week off 7h`. The **Week off** card is a third module-scope, harness-pinned piece beside `applyShiftEdit`: `weekOffShift(date, hours)` takes *any* day of the week and the hours of pay and answers `{ ok: true, shift }` (or `{ ok: false, field, error }`) with that row — hours, no clock times, the note `week off`. It is dated on the **week's Sunday** (`weekStartOf`), because a pay week runs Sun → Sat and the Sunday is the date that says which week the row belongs to; the card promises in `shiftPreviewLine` over `shiftPay`, so what it shows and what the week card pays are one piece of arithmetic. Dating a week off on the Sunday is only safe because of the pay rule that goes with it: `shiftPay`'s Sunday ×1.5 is a premium for *working* Sunday, so it follows the clock times — a row with hours and no times pays the card rate (7h → €101.08, not €151.62), and only a row carrying `special` itself pays the premium. Before that rule, a Sunday-dated week off was silently paid €151.62. Add rules to `weekOffShift` (+ the pay rule to `shiftPay`) and `scripts/test-tesco.mjs`, not to the card.
- **A recorded Tesco pay reaches the ledger by itself, on the sheet's own pay date.** Recording a week's pay in Tesco Pay — an imported tax table, a typed Final Bank Pay, a payslip figure typed into the card — writes that week's *Tesco pay* entry into the ledger at the pay date (`payDateOf`: the week's Sunday + 11, the Thursday the sheet pays on), so the tab and the ledger hold one figure rather than two opinions about one payment. The rules are `tescoPayLedgerWrites` in `tesco-pay.js` (pure, pinned in `scripts/test-tesco.mjs`); the write and its undo are `recordTescoPayToLedger` in `app.js`; what it wrote is remembered per pay date in `settings.tescoPayLedger` (`{ id, amount }` — validated in `storage.js`, merged per date in `sync-merge.js`). Three rules, each one a way the ledger could otherwise disagree with the tab: a pay date the ledger is silent on is **created**, unless any income already sits on that date (a Fill, a payslip typed into the Add screen — the user's own line wins); a pay date this app wrote before is **followed** only while the line is still the one it wrote — the entry is there, at the amount written — so a corrected bank figure moves it and a figure the user has since retyped does not; and a pay date in the record whose entry is **gone** is a line the user deleted, which is never written again. That last rule is the whole reason the record exists: without it the next recording of that week would write the deleted line back and the money would keep returning. Nothing here ever *removes* an entry, and a week with nothing recorded is never written at all — a shift-only week's simulated net stays an estimate, so `receivedByPayDate` leaves it out and the month card's Received is the one place an estimate is counted. All three read inside a **window** — see “only ever writes inside one window” below for why an unbounded one is what moved a balance by €11,000 in one run. The trigger is a Tesco commit (import, bank pay, shift add/edit), where the write joins that commit's own undo — a recording is ONE undo step and the toast says what reached the ledger (`Final bank pay saved. Updated €1750.00 to Balances.`) — plus the payslip-typing settle, which has no commit behind it (those fields commit on a timer so a caret survives) and takes an action of its own. Entry shape is Fill's own (`Tesco pay`, category misc, and `TESCO_PAY_METHOD` — see the next bullet for why that is the bank), so the dashboard, the CSV and the budget rules see one kind of line whichever way the money got there.
- **A recorded Tesco pay lands in the bank, and the method id is what makes that true.** Every writer of a *Tesco pay* entry — the per-row Fill, Auto-fill, the amount modal and the automatic recording above — writes `TESCO_PAY_METHOD` (`'AIB'`), one constant exported by `tesco-pay.js` rather than four copies of a string. It is not a label: `balanceDelta` counts a **credit on a gift-card method (TG/LG/AG) as a card LOAD**, so a week's wages written on TG did three wrong things at once — added to the Tesco card's balance instead of the account's, counted as `loaded` on that card (its “recorded loads” read as if the card had been topped up), and left the account the payslip actually paid into short by the whole week. The constant is pinned against `seed.js`'s own method list and against `GIFT_CARD_IDS` in `scripts/test-tesco.mjs` (a future change pointing Tesco pay back at a card fails the build), and so is the *fallback* amount: `lastTescoPayAmount` finds Tesco pay lines by their **own label**, not by method, so a ledger already holding entries from when they went on the card keeps counting them — a method filter would have silently dropped that fallback to zero for everyone who had filled a Thursday before the fix. A line already in the ledger is not migrated by this: the entry is the user's, and moving money between two balances is theirs to decide. Verified live in the served app: the line appeared at week + 11, a correction moved it, a hand-edited figure stopped it moving, a deleted line stayed deleted through a later recording, Undo gave the date back so recording again wrote again, and one Undo reverted a bank figure *and* the line it wrote. 10/10 mutations caught.
- **The recorder only ever writes inside one window, and what it wrote can be taken back.** The three rules in the “reaches the ledger by itself” bullet above had no bound, so the FIRST Tesco commit after the deploy ran them against every pay date the tables had ever held: measured on six months of payslips that is **25 lines / €9,377.75 in a single run**, and it is how a balance the user had been managing by hand went **4,000 → 15,000** without anyone asking for it. The drama was never a wrong sum — every figure in the path is 2dp and `fmt`-rendered — it was an unbounded catch-up. `tescoPayWriteWindow(today)` returns the current month up to today, `tescoPayLedgerWrites` **creates nothing without a window** (an absent bound must read as “create nothing”, never “create everything”, and a window whose ends are the wrong way round is dropped rather than widened), and `recordTescoPayToLedger` hands one in. The window is not an arbitrary slice of history: it is exactly the set of Thursdays the tracker card lists (`thursdaysInMonth`, filtered to `d <= today`), so a line can never appear for a date the card does not show. `receivedByPayDate` gates the same way on `payDate > cutoff`, so no line is dated ahead of the money either — a shift-only week in the month being paid next is left out until its Thursday arrives (a typed bank figure is the one exception: the user watched that land). The other half is **reversal**: ☰ → Data → **Remove automatic Tesco pay lines** appears only while `appWrittenTescoLines()` finds some, removes them in one undoable step, and **keeps `settings.tescoPayLedger`** — a mark whose line is missing reads as “the user deleted this”, so clearing the record would hand the whole catch-up straight back at the next recording. It never touches a line the user filled themselves, because only the recorder writes marks. Pinned in `scripts/test-tesco.mjs` (the window's edges, both `today` wirings, the card's own set, the repair's scope and its refusal to clear the record), **8/8 mutations caught**, and verified live in the served app: the row reported `1 written by the recorder, not by you` beside a hand-filled line it left alone, removed the marked one, and Undo gave it back.
- **A hand-filled Tesco pay line stays deleted, and the tag that does it is also why the repair can still say “not by you”.** The three rules above only ever saw *the recorder's* marks, so a Thursday the user filled by hand and then deleted in History looked simply **unfilled** — and the next Tesco commit inside the write window wrote the money straight back, which is the same “the money keeps returning” failure the record exists to prevent, just one step over. Fills now leave a mark of their own: `withTescoFillMark(marks, date, id, amount)` in `app.js` writes `{ id, amount, by: 'fill' }`, and all four fill paths go through it — the per-row **Fill**, **Auto-fill**, and the amount modal's single-date and bulk branches — each capturing `wasMarks` first and restoring it in the same `trackAction` (an undone fill must not leave a mark pointing at an entry that no longer exists, which reads as a deletion and silences the recorder on a date nobody asked it to leave alone). `tescoPayLedgerWrites` then skips such a date **entirely**: not created over while the line exists, not recreated once it is gone, and **not moved** when the week's figure later changes — a figure the user typed is their reading of what landed, not this app's. Two consumers had to be told, because the tag widens a record both of them read: `normalizeTescoPayLedger` carries **only the exact string `'fill'`** (an absent tag reads as the recorder's own, which is what every mark written before the tag already is, so an older document is not reclassified by the load, and an unrecognised value is not believed), and `appWrittenTescoLines` filters `m.by !== 'fill'` so the repair never removes a line its own toast promises to leave alone. The merge needed no code — a pay date is already taken whole from the fresher side — but it needed pinning, because a tag that did not travel would turn a fill back into a recorder line on the other device. Pinned in `scripts/test-tesco.mjs` (**541**, +8) and `scripts/test-integrity.mjs` (**249**, +5), **7/7 mutations caught** (the skip dropped, the helper stopped tagging, the repair counting fills, either undo or call site losing its mark, the tag dropped on load, an unrecognised tag believed).
- `aria-label` is an addressed identity, not a label: `restoreFocusedField` looks fields up by it, and the harness probes by it. Two controls on one screen sharing one is a bug — the edit sheet's fields are `Edit shift …` precisely because the Add-shift card already owns `Shift …`.
- The roster-photo reader (`tesco.js`) is harness-pinned too, and it is the piece most likely to be broken by a local change. Keep every step pure where it can be — the geometry helpers `dedupeWords`, `pageSkew`, `columnAnchors`, `resolveColumnDates`, `ocrEstimateTilt`, `ocrAutoContrast`, `ocrSauvola`, `ocrLocalMarks`, `ocrIllumination`, `ocrRulingLines`, `rosterColumnsFromRules`, `rosterReadQuality` take plain word lists / grey buffers and are covered by `scripts/test-tesco.mjs` ("the sheet's own geometry", "the page as ink and paper", "which reading of a photo to believe"); the pixel passes (`decodePhoto`, `levelPhoto`, `turnPhoto`, `ocrRosterRow`, `ocrPageWords`, `ocrOwnerCells`, `ocrPhotoRules`) are covered by `ocr-harness.html`. The pixel layer itself lives in `ocr-pixels.js` — one copy, imported by the reader *and* by its prep worker, because a threshold with two implementations is a threshold that can disagree with itself — and it was split out of `tesco.js` with its functions byte-for-byte the same (proved once by diffing them against `git show HEAD:tesco.js`). One of the four has since been deleted outright: `ocrStretchCanvas`, the context-shaped wrapper, ended up with no caller anywhere — the cell pass paints its own per-mode views and every strip/page read goes through the prep worker's `ImageData` — so dead exports were cleaned in the same pass (`rosterNameColumnRight`, `groupWordsIntoRows`, `drawPhotoPreview` lost their `export` keyword; they are called, just not from outside `tesco.js`).
- The reader assumes the page's geometry is the *sheet's*, not the pixels': a tilted photo is levelled once (`ocrEstimateTilt` → `levelPhoto`) before any row/cell work, a sideways photo is retried after `turnPhoto` ±90°, and the 50 % strip overlap's duplicate words are collapsed by `dedupeWords` before parsing. When a date token disagrees with its column's weekday name, the weekday name wins — the day names are what `resolveColumnDates` trusts, and the week containing today is the fallback, not "the next Tuesday". The levelling search reaches ±8.5°, the same bound `pageSkew` trusts from the words: an estimator that stops at 6° reports a 7° sheet as 6° and levels it 1° wrong, which is enough to crop every cell onto the row above.
- **The strips are the cheap reading, not the deciding one.** `ocrRosterRow` offers every reading of a photo to `rosterReadQuality`, which scores it on what it actually produced (columns, the typed name on a row, dated shifts on that row, dates distinct, and a header the week could be dated from) and the reader escalates — page, then locally-thresholded page, then the photo turned a quarter turn — until one comes back *complete*, keeping the best score otherwise. A read that **merely mentions the typed name no longer ends the scan**: a read can carry the name and still put the week's shifts on the wrong days (that is exactly what a photo lit from one side does). `read.tries` on the result records what each reading scored, and the harness prints it.
- **A rung of the ladder is a batch, run on a pool of engines.** The readings a rung is made of are independent of one another — three strips, then the plain page and the thresholded page, then both quarter turns — so `ocrRosterRow` takes them together on `createOcrPool` (at most three Tesseract workers, created on demand, `ocrPoolSize(hardwareConcurrency)` cores-1 capped at 3) and feeds the results to `consider()` **in the order the one-after-another ladder reached them**. That is what keeps the change honest: the `tries` list, the `scanned` count, `pagePass` and the reading believed are the serial ladder's, and `reads=` on the harness line still counts the readings the answer rests on rather than the ones the pool had in flight. Two rules make the pool safe. Reads on ONE worker must stay sequential, because tesseract's character whitelist and page-segmentation mode are *worker* state — and the corollary is that a batched read **must name the mode it wants** (`psm: '11'` on the turns; `ocrReadCell` sets `'7'` with every cell read rather than once for the pass) instead of inheriting whatever the rung before it left there, which with several workers would depend on which one happened to be free. And each read in flight draws into a surface of its own (`ocrScratchCanvas`) — a read is `draw → stretch → toBlob → recognize`, and the two awaits in the middle are where a shared canvas starts a second draw over the first read's pixels. That is now true of both the ladder's strip and page reads (`prepEncode` draws and reads back on one, then hands the bytes to a prep worker) and the cell pass. The caller's canvas is only the on-screen preview now, so `ocrRosterRow`'s `finally` zeroes it itself, the preview the scan started from (`discardPhoto`) being the same element. Cost profile, measured pairwise on the harness's lamp scenarios: the recognize is 13–25 s of a strip read against ~1.4 s of preparing one, and it grows with how much text the engine finds, not with pixels. Three readings in flight return about 1.9× the throughput of three in turn on a shared machine — but the real gain is pipelining, the main thread preparing the next reading while the engine works on the last, which is why the badly lit photos (77 s → 52 s on `tilted-7deg-lamp`, 45 s → 23 s on `uneven-lamp`, paired and counterbalanced) gain most and a photo the strips settle gains least. The cell pass is a batch of the same kind: `ocrOwnerCells` takes the pool rather than a worker and submits the name read and every day column together — `ocrOnScratch` gives each its own surface, and the bar walks the week as the days come back — measured at 150–400 ms against 220–590 ms one at a time. That is small because a cell is a ~0.1 MP crop, but it is the tail of every successful scan and the pass that grows with the width of the week. Adding a rung means adding a batch, not a `for` loop.
- **Preparing a read is a thread of its own** (`ocr-prep-worker.js`). A read's image is drawn, binarised and PNG-encoded before the engine sees it: on a 12 MP strip that is a draw (~30 ms), a readback, a threshold (~490 ms) and an encode (~1.7 s on the reader's thread, 0.5–0.6 s in a worker — `convertToBlob` is the faster encoder), and the reader's thread was busy through 316–684 ms of it. Measured interleaved on one machine with a `MessageChannel` ping loop, which is the only honest way here: a hidden tab throttles `setTimeout` heartbeats and reports stalls that are not there. That blocking is the one part of a scan that could not overlap the engine — while a strip was being encoded the reader could not start the next reading, collect the one that finished, or repaint the bar. So the threshold and the encode run on prep workers, and the reader's thread keeps the draw and the readback that turn the canvas into bytes worth sending: **151–292 ms of longest stall, and prep 1.4–1.8 s → 0.4–0.6 s**. `ocrStretchData` (in `ocr-pixels.js`) is the function the worker calls — on an `ImageData`, which is what makes the threshold testable in Node at all (a plain buffer, no canvas) — while the reader's cell pass does its own per-mode views on a scratch canvas (`ocrCellImage`: histogram stretch, `ocrFlatField`, the row ink cut). The pool is `createOcrPool` again, sized by `ocrPrepSize(cores)`: whatever cores the engine pool (`ocrPoolSize`) and the app are not using, at least one, at most `OCR_PREP_MAX` (3). `ocrStripBox`/`ocrPageBox` decide the region, the working size and the threshold's glyph window in one place, and they stay on the reader's side of the wire on purpose — every box the engine reports is mapped back through them (`kx = box.sw / box.w`), so a box computed in two places is a box that can disagree with itself. Both are pinned in `scripts/test-tesco.mjs` ("the prep workers a read's pixels are prepared on") with the job protocol: a reply is matched to its job by id (a rung asks for three strips at once and they come back in the order the engine finishes them, not the order they were sent), a job the worker could not do fails that job alone, and a worker that died — a script that would not load, a `terminate()` mid-read — fails every read waiting on it *and every read asked for afterwards*, because a scan that hangs is worse than one that fails with a reason. Nothing outlives the scan: the buffer is transferred rather than copied, the reader's scratch canvas is zeroed on every path, and `disposeOcrWorker()` now drops the prep pool beside the engine pool, so `scripts/check-image-hygiene.mjs` lints three files rather than one. Two things this design learned the hard way, both of which the harness caught and neither of which `node --check`, the guards or the app path could: **the worker may not draw the photo itself.** Handing it a cropped bitmap to draw and binarise (5 ms of reader thread) shifts 1,716 pixels of a 12 MP strip by up to three grey levels — `drawImage` resamples a source rectangle and a pre-cut image differently, and a worker's OffscreenCanvas differs from the main thread's by ±1 even from the full bitmap — and that was enough to flip `blurry` through the cell pass, which cuts its crops from the word boxes the image produces. So the reader draws and reads back, and the engine is handed the image it was always handed, byte for byte. And **the cell pass never goes through the pixel layer at all**, which is how the context-shaped `ocrStretchCanvas` wrapper went dead and was deleted rather than kept as an export only a doc comment could justify: `getImageData`/`putImageData` are context methods, so a canvas handed where pixels belong is not an error a scan can report — its own `catch` returns `'stretch'` with the image untouched, so the scan still finds a row on a good photo and only the sheet lit from one side comes back as noise (the harness's `uneven-lamp` and `tilted-7deg-lamp` scenarios are what catch a view that never ran; `clean` and `sideways-90` passed throughout, a photo whose paper is already white paying `ocrAutoContrast` nothing).
- **Two binarisations, and the photo picks.** `ocrStretchData(img, view)` — run by the prep worker on the pixels — gives the engine either a global contrast stretch (`stretch` — keeps the grey the LSTM reads, and the anti-aliased edge of a stroke) or a local Sauvola threshold (`ink` — segmentation the engine's own global Otsu gets wrong; tesseract's maintainers call theirs "rather bad quality" and it is what every layout decision is made from). `ocrIllumination` measures the photo's own light (the spread of the *paper* level between tiles, so text does not count as unevenness) and the escalation picks the view from it. A photo the reader can read never pays for the second view.
- **Rules beat names for the column boundaries.** `ocrLocalMarks` (mean − C, not Sauvola — a hairline table rule is far too faint for a glyph threshold) → `ocrRulingLines` (long contiguous runs, never ink counts) → `rosterColumnsFromRules`, which returns a grid only when it has seven columns *and* every column the words found falls inside the span that claims it, so refining the grid can straighten a crop but never move it onto another day. The name column's right edge is a rule on every ruled roster, and that is the boundary `rosterNameColumnRight` needs to be right.
- **A day column the header did not give up goes back into its own gap** (`columnAnchors`): a column's date is derived from its *position* in the row, so filling at an edge renumbers every day after it. Read at an angle with the light falling off, the header loses one day from the middle and a left-edge fill turned Tuesday's shift into Wednesday's — a whole week paid a day late, the one misread nobody notices. Only when there is no gap does the fill go to the left edge, where a phantom day is numbered *before* the week and takes no shift the day names did not already date.
- **The reader reads the paper's grammar, not the engine's.** Five rules, each pinned in `scripts/test-tesco.mjs` (`the cell's words`, `the sheet's own geometry`, `which reading of a photo to believe`) and each a way a legible photo used to be refused or, worse, mis-dated:
  - **A minute separator is a colon, a full stop or a comma**, and a typographic minus is a minus (`parseTimeCell`, `CELL_RANGE_RE`). A colon is two dots and JPEG ringing closes the gap between them, so the engine hands back `07.00-15.00` — a whole shift, thrown away over its punctuation. A plain number is excluded (`12.40` is not a time) and a three-number date is not one either.
  - **A date may name its month and print its year** — `27-Sep`, `20 September 2026`, `22-Sep-2026` — and a printed year is obeyed even when the nearest-year guess would differ, which is what makes the turn of the year safe (a roster for the week of 29 Dec, photographed on 2 Jan, dates December and not the December after next). The month-name branch only claims a middle token that really has a letter in it, or `22/09/2026` — day, "month", year — would be read as a month name and answered `null`.
  - **A title's date range is found INSIDE a phrase, not only as one** (`dateTokensIn` → `rowDateTokens`). The engine boxes a run of print as a single word, so `Week 39 22/09/2026 - 28/09/2026 Store 3021` comes back whole — and reading only whole phrases threw away the one line that says which week the sheet covers, which is also the one line big enough to survive glare. Both rules that count a header's dates go through it (the band rule in `parseRosterWords` and the date-row choice in `columnAnchors`); which dates may *anchor a column* is still judged phrase by phrase, because a column needs a position and a phrase has one.
  - **When the title's range and the grid's day names disagree, the names win** (`resolveColumnDates`). A Monday-first range printed over a Sunday-first grid is a day out, and a week dated a day late is the misread nobody catches; the series is therefore slid by whole days to the offset the day names agree with most. It is a *slide*, not a re-dating: the range still says which week, and a range more than half a week out is a different week the slide is not allowed to invent.
  - **Corroboration is measured, scored and required** (`columnDatingAgreement` → `rosterReadQuality`). The dating is one rigid series, so how many of the sheet's own day names agree with the dates they were given is the whole of the evidence behind the week: it is worth two points a name when the reader picks between readings of one photo, and `complete` demands three agreeing names (or all of a shorter run). What that replaces is `named >= 3 || dateTokens >= 3`, which accepted a header of seven names of which two agreed — a header that describes no week at all, and one the reader would then stop on. There is deliberately no "contradicted" outcome: with one name the dating can always be slid by under a week to honour it, so "no name agrees" is not a state a real grid reaches, and low agreement is what a garbled header actually produces.
- The harness photographs the two new rules too: `dot-times` (a colon read as a dot) and `title-range-one-day-out` (a range one day out of step with the grid's first column), and its `readings:` line prints `n` names present and `a` of them agreeing — the number that says whether a week was read or guessed at.

- A week's **final bank pay** is typed off a bank statement, so no formula derives it (holiday pay, a refund, a correction all make it differ from gross − tax) — and it is a *week's* figure, not a row's, which `buildPayWeeks` enforces by summing the figures it finds (a payslip's when any payslip of that week has one, otherwise the shift rows'). Writing one figure into two homes would pay it twice, so the rule is a module-scope, harness-pinned function: `weekBankWrite(shifts, payslips, carrierId, amount)` sets it on the week's **carrier row** (its first row by date — the row `tescoCsv` puts a week's figures on) *and* on the week's own payslip (the last of that week), and clears it from every other record of that week. A blank or unreadable amount clears the week (`null` = not known, and the received line hides) rather than quietly zeroing it; it is copy-on-write, so an unchanged figure hands back the same records and the cell can tell an edit from a click-through. The cell that takes it sits in the shift row's tail — `[gross][Bank][pencil][×]` as one group, which wraps whole to its own line on a phone — and it exists on the carrier row only, one per week. It commits on **change, never on input** (the same reason the week-number field beside it waits for change: `render()` rebuilds the screen and a rebuilt number field has no caret to keep), which is why `writeWeekBank` can commit through `snapshot`/`commitTesco` for one undo step. `actualFigures` shows the received figure whenever the week has one, payslip or not — it used to need a payslip, so a net typed on a row counted in the month's total with nothing on the week to say so. Add rules to `weekBankWrite` + `scripts/test-tesco.mjs`, not to the cell.
- **The week card's `vs est` chip compares two figures of the same base, and names the base it used.** `weekVsEstimate(w, rates)` in `tesco-pay.js` (pinned in `scripts/test-tesco.mjs`, "the week card's vs est chip") answers with `{ against, delta }` or null, and `actualFigures` only prints it: a week with a bank figure is measured against the estimate's **net** — the two figures a week can be checked side by side against a statement, `Received €469.78` against `→ net €470.59` = `−0.81 vs est net` — while a payslip-only week (no net recorded, so no net to compare) is measured against the estimate's **tax plus its pension**, because a payslip total is PAYE+USC+PRSI+FF and a net is a different figure entirely (`vs est tax`). Before this the chip compared what it had against whichever base was at hand: that same week's net against the withholding total printed **`+0.81 vs est`** beside a net estimate, a number belonging to neither line and with the sign of the comparison rather than of the money. The sign says which way (negative is short of the estimate), the €1 good/warn threshold is unchanged, a bank figure with no payslip now gets the chip too (it used to need a payslip, so a typed net showed a received line it was never reconciled against), and a week with nothing recorded — or no gross to estimate from — has none at all.
- **The dashboard's Tesco pay tracker reads its figure out of Tesco Pay, and the join is the pay date.** The `Tesco pay · Thursdays` card in `screenDashboard` fills a Thursday's ledger entry from the week that was *paid* on it — `payDateOf(weekStart)`, a week's Sunday + 11, which is the date the entry itself carries — instead of repeating the last Tesco entry's amount, which is what it did before: ten weeks of the same figure are a guess that is only right while the pay never changes. `receivedByPayDate(shifts, payslips, rates)` in `tesco-pay.js` (pinned in `scripts/test-tesco.mjs`, "what each pay date brought") answers one `{ amount, source }` per pay date, and the sources are not the same kind of number: `bank` is a typed Final Bank Pay (money the user watched land) and `recorded` is the week's own arithmetic, gross minus the tax its payslips withheld (the sheet's Calculated Income). Both go through the same `weekReceived` the tab's *Received this month* counts, so a Thursday's entry and the tab's Received for that week are one figure rather than two opinions about one payment — pinned by asserting both in the same section. **A week with nothing recorded is deliberately absent.** Its simulated net is an estimate, and an estimate written into a ledger as income is a wrong figure nobody sees arrive; the month card may count it as received, the ledger must not, which is the one place those two deliberately diverge (the divergence itself is pinned). Such a Thursday keeps the old last-amount behaviour, and the modal is asked for only when that leaves nothing to fill at all (and then only for the Thursdays it could not fill). The fill is per Thursday, not one figure for all of them: `Auto-fill` fills each with its own week's figure where there is one and the fallback where there isn't, in one undo step for the batch, and the toast reports the total and how many Thursdays were left to fill. The card prints the figure it is about to use beside the `Fill` button (with the source in its `title`), because a number that turns up in the ledger unannounced is indistinguishable from a bug.
- The tax estimate is the sheet's Potential Tax formula (`simulateTax`) with **one deliberate divergence at low earnings**, pinned in `scripts/test-tesco.mjs` ("PRSI: the low-earnings rules"): **an employee on €352 a week or less is exempt from PRSI**, and above that the €12 weekly credit tapers away by one-sixth of the excess over €352.01, reaching nothing at €424, above which the charge runs straight through on every euro of the week. The sheet charged the full rate below the threshold, which over-stated a €300 week (about 20 hours at the card rate) by €12.60 — such a week owes €0 PAYE (the €76.93 credit swallows it), €0 PRSI and only the USC, so €2.54 out, which is what a payslip shows, against the €15.14 the old formula claimed. The workbook parity the harness pins (`€550.525 → 33.18 / 7.55 / 23.12 / 8.26 / 63.85 / 478.42`, and the CSV row the export writes) therefore holds for weeks **above** the threshold, and the €287 Sunday pin's label carries the difference — it is the one cached cell the app intentionally no longer reproduces. Two things are deliberately **not** modelled, both because a weekly simulation cannot see them: the **USC exemption** (total income of €13,000 or less pays none — applied per week it would zero any holiday week for a year-round worker) and the **PRSI rate change of 1 Oct 2026** (4.2% → 4.35%). `TESCO_RATE_DEFAULTS.prsiRate` stays at the workbook's 4.2% so its rows survive an export unchanged; the rates card names both rates and that field is the user's to set.
- The Tesco stats card's three figures sit on **two bases, and each label says which** — pinned in `scripts/test-tesco.mjs` ("what a month's figures mean") with a fixed `TODAY`, because one rule is about dates and a harness reading the wall clock would change its answer on 1 October. *Hours this month* is the month's own shifts, by shift date. *Anticipated (est. net)* is a **net**, and a net is weekly — the PAYE credit, the USC bands and the PRSI threshold are all per week — so `simulateTax` runs **once per pay week on the week's whole gross**, never per row (each row would take its own credit: two €500 rows of one week pay €153.84 of PAYE between them, not €46.14), and the week is placed in the month its **Sunday** falls in, the sheet's own month rule, so a week straddling a boundary is counted once and never prorated. *Received this month* is money that **landed**, so it follows the **pay date** (`payDateOf`, week start + 11, the date every week card prints) and not the week: the week of 27 Sep is paid on 8 Oct and is October's, while the week of 30 Aug was paid on 10 Sep and is September's — reading the month off the week's start moved both edges the wrong way. `receivedTotal` takes each week's money in order of authority: a typed **Final Bank Pay** (which counts whenever it is dated, because the user watched it land), else `gross − recorded tax` (the sheet's Calculated Income, a refund week's negative tax landing as money in), else the week's **simulated net** — the same "→ net €X" the week card prints. A payslip with no shift rows beside it is the one week nothing can be derived for: its tax says nothing about the gross it came out of, so only a refund is money in. The estimate is the fix for a real defect: an unrecorded worked week used to be worth **€0** (the old `w.payslips.length && w.shifts.length` guard), which is how a month with three worked weeks and one payslip added up to that one bank line while the card still called the result "received" — and it also read a refund-only week (the case this module's own header names) as €0. A week is counted only once its **pay date has arrived** (`today`, the last parameter of both `monthSummary` and `lifetimeTotals` — pass it, don't reach for a clock), so an estimate can never claim money the bank has not paid yet. Both figures are nets on both surfaces (the card and the dashboard's Tesco line).
- A figure derived from a field rides that field's **label line** (`.tesco-numfield-label`, e.g. the Sunday rate card's `= €21.66/h`), never a trailing line under its input: a line only one cell had made that cell taller than the one beside it, so the rates grid's rows were spaced 30px then 10px and — sized to its contents — that one cell came out 30px wider than its five neighbours. The grid itself is CSS `grid` with `minmax(0, 1fr)` columns (2 / 3 from 640px / 6 from 950px, the width six columns need to hold the Sunday label's own 114px), not a wrapping flex row: wrapping broke it 4+2 on a tablet and 5+1 just below where all six fit. The hint is `nowrap` so it cannot wrap the label at 320px.
- `sw.js`'s `SHELL` array is read by two guards (`check-sw-shell.mjs`, `check-boot-payload.mjs`) with a naive quoted-string scan, so **keep comments out of it** — one apostrophe pairs with a real opening quote and shreds the list (it did: “dashboard's”). Everything the app loads belongs in it, statically *or* lazily: `check-boot-payload.mjs` fails when a module the app imports is missing from the shell, which is how `/ocr-pixels.js` turned out not to be warm for a first offline visit to `#tesco`. The OCR engine itself (6 MB of wasm + traineddata) is deliberately not precached — a cold offline scan cannot work anyway.
- `render()` rebuilds the whole screen, so never call it from a field's `onInput`: app.js restores focus by aria-label but not the caret, and a rebuilt `type=number` field has no selection API at all (`selectionStart` is null), so the next digit lands at the wrong offset. Update the field's own row in place, debounce the figures around it, and paint once the caret has left the card — see `refreshDerived` / `repaintAfterPayslipEdit` in `tesco.js`.

## Security Invariants (do not regress)
- CSP in `_headers` pins SHA-256 hashes of the 5 inline scripts in `index.html` — **editing any inline script requires re-hashing or the app won't boot** (browser console reports the correct hashes).
- `lib/tokens.mjs` = AES-256-GCM setup tokens, single-use via `lib/store.mjs` (the KV store; in-memory fallback where no store is bound), keyed by the deployment's root secret (`lib/secret.mjs`: `CENTS_SECRET`, or `GITHUB_TOKEN` for a deployment configured before that name existed). Password must never appear in URLs.
- Both functions: constant-time password compare (`lib/auth.mjs`), per-IP failure throttle, `APP_PASSWORD` ≥ 8 chars.
- **A phone is two prerequisites, neither visible from the server** (pinned in `scripts/test-reminder-push.mjs` 0d). A Chromium-based Android browser subscribes from an ordinary tab, but it refuses a subscribe whose notification permission is *denied* — and the prompt itself only opens inside a user gesture — so `subscribeReminderPush` asks first and answers `permission-denied` / `permission-blocked` (a denied permission can never be re-prompted, so the way out is the browser's own site settings) instead of letting `subscribe()` fail with something that names the wrong thing; that misreport is also how a bad server key came to be reported as "network error" on a phone. The Android browsers still on the GCM path (Samsung Internet, Opera) additionally need `gcm_sender_id: 103953800507` in `manifest.json` — Chrome's own push sender id, a public constant and the same for every site, not a per-project number. iOS is stricter: Safari will not subscribe at all until the app is on the Home Screen, which the app can only report, not fix.
- **The push signing pair is resolved in exactly one place and checked before it is trusted** (`vapidConfig()` in `lib/webpush.mjs`, called by `reminders-push.mjs`'s GET and test push and by the reminder run (`lib/reminder-run.mjs`)). `VAPID_PUBLIC_KEY` is served on an unauthenticated endpoint by design — a browser needs it before it can subscribe — so a pair pasted the wrong way round puts the **private seed** in public: it happened on this project's own deploy, which answered `200` with the 43-character seed as its `publicKey`, and push was broken twice over, since no browser will subscribe with 32 bytes either. So the configured pair is used only when the public half is a 65-byte `0x04` point *and* the private half derives it; otherwise the pair is **derived** from `GITHUB_TOKEN` (HKDF-SHA256, info `cents/vapid/derive/v1`, salt `cents/vapid/keys/v1`, retried until the scalar is in `[1, n-1]`), which is what makes the endpoint self-configuring on a site whose environment was never touched. Two properties are load-bearing and both are pinned: **the derivation must be deterministic and both halves must resolve through it**, because a browser binds its subscription to the key it subscribed with and a push service rejects a JWT signed by any other key — a drift between the endpoint and the sender is a silent non-delivery — and **`APP_PASSWORD` must never be key material**, since it is short, human-chosen and readable by the user while the derivation is public in this file. `scripts/test-reminder-push.mjs` covers it (0c, 13; 3/3 mutations caught), and (12) pins the dispatcher's own clock: a record in a zone ahead of UTC is due at *its* local time and its once-a-day marker is that zone's date, not UTC's.
- **A VAPID JWT's signature is the fixed-width pair, and nothing in this repo checked one until it had already shipped.** `vapidAuthorization` signed correctly but copied node's DER integers into the JWS as-is, and DER's INTEGER encoding is *minimal*: it drops a leading zero byte from a value that does not need one and adds a zero sign byte to a value whose top bit is set, so each half comes back 31, 32 or 33 bytes. Measured on 400 signings: 199 came out 65 bytes, 95 came out 66, one came out 64 with its two halves still the wrong ones — **74 % of pushes could never have been accepted**, and the phone showed nothing for a message the app called *sent*, while the daily reminder failed at the same rate. JWS (RFC 7518 §3.4) wants `r || s` at exactly 32 bytes each, so each integer is now re-fixed to its last 32 bytes (padded when DER dropped a zero). The reason it went unnoticed for a whole feature's life is the harness: its fake push service decrypted the aes128gcm body like a browser but **never verified the Authorization header**, and the one check that looked at the header asserted the `k` inside it — a check that a signature nothing ever validated passes. The fake service now *authenticates* before it looks at the endpoint (401 on a bad JWT, like the real thing), and 0e signs **24 messages** rather than one: a single signature is a 1-in-4 coin flip when the bug is present, which is exactly how a one-shot check would have passed it. 2/2 mutations caught (copying the DER bytes through again; keeping the wrong end of a long integer), each failing most of the suite, not just the new check — with a strict service, a broken signature is a delivery that does not happen anywhere. **And the two ways a delivery ends that are not "the subscription is dead" are pinned beside it (7b, 3/3 mutations caught):** a service that *answers and refuses* is a status the test push names (`Push service rejected the test message (HTTP 503)`) and the scheduled run counts (`rejected=` in its one-line summary), while one that *cannot be reached* is no status at all — transient, not counted, and left due so the next slot can try again. `sent=0` on its own was the same line for a service refusing every message and a quiet day, which is exactly why the counter exists. The unreachable case is reproduced with a port that was just closed: destroying the socket on the server side is not the same thing, because the client's `fetch` then waits for a response that never comes instead of failing (that hung the suite for five minutes before it was noticed).
- **A push service answers 404/410 to a registration it has not been told about yet, and that verdict is this app's own "this device is dead, drop it" signal.** Measured live against real FCM, one first-ever subscription per browser: a push sent **0.01 s and 0.51 s after `subscribe()`** came back 404/410, and the same push at 1 s — and at every longer delay — was accepted. So the one flow this feature exists for (press *Enable push*, then *Send test push* in the same breath) deleted the stored subscription and told the user to re-enable push, over a device that was perfectly healthy. It was found in the scheduled path: the daily sender's first attempt at a **second-old** record answered 404, `pruned` it, and the next run had nothing left to send to. Which verdict is which is therefore decided by **age** — `subscriptionWarmingUp` / `pushSendWarming` in `lib/webpush.mjs`: a `gone` on a record younger than `PUSH_WARMUP_MS` (30 s) is asked once more after the measured window (`PUSH_WARMUP_RETRY_MS`, 2 s), and reported as **`warming`, a result with no `gone` key at all**, because both callers delete on that key. Two details carry the feature: a record with **no readable `createdAt` is not warm** (an unreadable stamp must not make every push immortal, and it is how the suite's hand-written records still reach the prune path), and the retry is **injectable** (`sleep`, `retryMs`) so the suite can exercise both asks without sleeping. The test push answers **425 with `Retry-After`** for a device that is still cold, and the app gives that its own reason — push stays switched ON and the modal says "tap again in a moment" instead of sending the user back to Enable push; the scheduled run counts **`warming=`** beside `rejected=` and prunes nothing, leaving the record for the next day rather than losing the user's setup. One retry is deliberately all there is: the window belongs to Chrome, not the app, and it does not reproduce on demand (three live samples at 0.00–0.03 s were accepted on the first ask, while another run had a registration still cold 2 s later) — so the **age gate, not the retry, is what guarantees nothing is destroyed**. `scripts/test-reminder-push.mjs` §7c pins the predicate's boundaries, the retry (two asks, one delivery), the 425-with-the-record-kept path, that an *established* record is still pruned on a real 410, the sender's `warming=`, and the client's ordering rule (425 is its own reason, and only a real 410 may clear the stored subscription) — **10/10 mutations caught**, two of which reproduce the shipped symptom exactly (`410 {"error":"Subscription is no longer valid - re-enable push"}`, `0 record(s)`).
- **The daily reminder fires at its hour, and never as a catch-up on the site being opened — and "whether the page is in front" is the wrong axis to tell those apart.** `startReminderScheduler()` runs `tick()` on `DOMContentLoaded`, so a day whose hour had already passed (default 20:00) raised a **system banner the instant the site was opened**: the user's experience of the "daily reminder" was a notification on open and nothing at 20:00, because 20:00 came with the app shut. The first fix for that suppressed the banner whenever `document.visibilityState === 'visible'` — which silenced the ONE case where a reminder is actually due, the app open and waiting at the hour, and it is why the reminder then "still didn't work". The axis is **time**: `tick(catchUp)` / `fire(catchUp)` / `showReminderNotification(name, { catchUp })`, where the scheduler's own **start-up tick is the only catch-up** (`tick(true)` — the hour passed by an unknown margin and the user is the one who just opened the app, so a banner there is a notification popping as the site loads, not a reminder). Every tick the app has been alive across passes `catchUp: false` and raises the banner **whether or not the page is in front**: the `setInterval(() => tick(false), …)` minute loop and the return to a backgrounded tab. The catch-up still marks the day done and still delivers the in-app toast, so opening the site after a missed hour nudges once in-app and cannot nag again. **Test now** is a plain call — no flag — because it is the button that exists to prove the banner works. Pinned in `scripts/test-reminder-push.mjs` (section 14: the start-up tick raises no banner but marks the day and reaches the toast, a tick with the page in front raises one, Test now raises one, no permission raises none, exactly one `new Notification(` construction site reached by `fire()` only through `showReminderNotification`, and the start-up/loop pairing itself), **6/6 mutations caught**, and verified live in the served app with a spy: importing a fresh instance and starting the scheduler produced **0 banners** with the marker set, and the running app's own minute loop produced **1 banner** with the page in front. **The open-app half is only half, and the gate that kept the other half phones-only was the same wrong axis.** A browser with no tab running at the hour has no local scheduler to run it — which is exactly the state the symptom above was recorded in, since the tab was closed at 20:00 and only path 1's start-up catch-up ever fired — and Web Push (`reminders-push.mjs`) is the one path that reaches it. `pushSupported()` gated that on the **user agent** (`mobileWebApp()`, a phone regex) for the feature's whole life, on the reasoning that on desktop the app lives in a tab on a machine that is on and the in-app scheduler is the right surface; the symptom disproves the premise. The gate is now the **capability alone** (`serviceWorker` + `PushManager` + `Notification`) and never the device, so a desktop subscribes like a phone — the phone-only extras it never had (`gcm_sender_id`, the iOS Home Screen rule) remain README's, and the server was already device-blind. Pinned in `scripts/test-reminder-push.mjs` (section 15: `pushSupported()` is true under a **desktop** UA and false when a capability goes, a desktop `subscribeReminderPush()` gets past the gate and stops on `no-sync` instead, `pushSupported` names all three capabilities, and no `userAgent`/device regex appears anywhere in `reminders.js`), **5/5 mutations caught**.
- **A daily reminder whose own record fails must fire once, not every minute — and must not disappear.** `tick()` reads the settings every minute and writes `lastFiredDate` from inside a `try/catch`, so both storage failure modes were silent and continuous: a full quota made the write throw and the next read said “not fired yet” → **a system banner plus an in-app toast every 60 seconds for the rest of the day**, from a reminder set once; and a blocked or corrupt read answered `normalize(null)`, i.e. `enabled: false`, so an armed reminder simply stopped existing for the session. `readSettings()`/`writeSettings()` in `reminders.js` invert that: the session's copy is the truth and storage is write-through, with `storageOk` dropping to false on the first failed read or write (after which memory wins) — and the cache is keyed by the profile key, because that key is what changes when a profile is switched, so a switch still re-reads whose schedule is running. Pinned in `scripts/test-reminder-push.mjs` (section 16, each scenario against its own module instance since `startReminderScheduler` is a one-shot): a blocked read still reports the armed reminder and still fires once, a refused marker write leaves the start-up tick at one toast and the next two minute-ticks at **no** banner, the cache is keyed, the write keeps the change in memory — plus the two-delivery check that `reminders.js` and the run in `lib/reminder-run.mjs` carry the **same `cents-daily-reminder` tag**, so a subscribed device shows one notification rather than one from the page and a second from the push service. **5/5 mutations caught.**
- **The daily reminder reaches a closed app with NO cloud sync — and a wake must never become a second notification.** The phone this path exists for has no sync password, so server push cannot serve it and the page's scheduler is not running at the hour. The third path is the browser's own **Periodic Background Sync**: `syncPeriodicReminder()` in `reminders.js` registers the worker's `periodicsync` event for an INSTALLED app — called on every start and from the reminder modal, gated on capability + **install state** (`display-mode: standalone`, because the browser only RUNS these wakes for an installed app, so a tab must be told `unavailable/not-installed` rather than armed) + already-granted permission (arming never asks — starting the app must not surface a prompt), with `minInterval` a **12h floor, never a schedule**: the browser picks the wake moments from engagement, which is why server push stays the on-time path and this is the safety net under both. A worker cannot read the page's localStorage, so the schedule `{ enabled, time, fired }` is mirrored into Cache Storage (`cents-reminder`, kept by `activate` exactly as it keeps `cents-build` — a deploy must not re-arm a delivered day) on **every settings write**, re-mirrored at every start, and read back before arming. Every path that shows a banner writes its day there (`markWakeFired` from `tick`, catch-up included — a user who opened the app after the hour was nudged in-app and must not get a late banner too — `markReminderFired` from push and wake) and reads it before showing one: the shared `cents-daily-reminder` tag only REPLACES a visible notification (`renotify` re-alerts), so the **record is the dedupe, in both directions**. The wake has three gates — schedule on (a wake is the browser's decision, not permission), hour passed (firing on any wake would put the reminder at whatever moment the phone felt like), day not already had — plus the record-older-than-yesterday catch: a device phase-locked to wakes before the hour would otherwise NEVER fire, and a late reminder beats a skipped one — and it YIELDS to an armed push before the hour, which is the bug the bullet three below this one is about (a catch-up that marks the day pre-empts the very hour it exists to cover). The modal's verdict is the register's own: `'on'` only after a register the browser accepted, `'unsupported'` for a browser without the API, `'unavailable'` + reason otherwise — the row promises a notification on that verdict alone, so it must never say "on" speculatively. Record writes are chained (`queueWakePatch`): `tick()` writes the schedule and the day back to back, and two patches in flight would each read the OLD record — the slower put wins with a stale base, and a `fired` written from before the mirror's `enabled: true` is exactly how a wake stops firing while everything on screen looks right. Pinned in `scripts/test-reminder-push.mjs` **section 18** — the REAL `sw.js` evaluated in a function scope with `self`/`caches`/`Date` injected and a fixed local clock (13 behavioral checks across wake, push and activate), the page's arming states (12), and the halves `app.js` cannot be imported for (source pins: each modal call site by its own shape, the permission gate, the chain) — **20/20 mutations caught**. Known limit, stated to the user: PBS timing is best-effort (Chrome may wake it late or, at a fixed pre-hour phase, every other day via the missed-day catch), so the on-time guarantee remains the server push. The boot ledger moved for it: the mirror and arming ride `reminders.js`, which is on the boot path by design — **700 KB measured / 725 KB allowed** at that commit (the running total lives in the boot-budget bullet above).
- **A reminder that arrives hours after its hour is a broken reminder, and two settings were what allowed it.** The sender is the on-time path, and its timing is the look-back window alone: `WINDOW_MINUTES = 10` in `lib/reminder-run.mjs`, deliberately WIDER than any caller's cadence, so a run that arrives late still catches its target instead of losing the day. The window has to be wider than the schedule, and that is exactly what used to go wrong: when it was matched to the schedule (`*/15` with a 15-minute window), an unaligned target fired up to a quarter-hour late and a single run the platform delivered 16+ minutes late fell outside every window and **skipped the day entirely**. The second half is on the wire: `pushSend` sent `Urgency: normal` with `TTL: 14400` — Android's doze defers a normal-priority message to the phone's next wake, so an on-time send was *displayed* hours later, at whatever moment the device woke, inside a 4-hour TTL that made that legal (the reported symptom: set 20:00, arrives at a random hour). Now `Urgency: high` (one notification a day is exactly what high priority is not an abuse of) and `TTL: 3600` (an hour-old "log your spending" is a surprise, not a reminder; the wake path still covers a day whose push expired). Pinned both ways: `check-worker-config.mjs` reads `WINDOW_MINUTES` from the lib and fails if it is narrower than a minute (the mutation it catches: a window of 0, which would skip the day's reminder on every run), and `test-reminder-push.mjs` captures the request headers at its fake service (`push-is-high-urgency`, `push-ttl-bounds-lateness-at-an-hour`; 2/2 mutations caught). The push/wake double-fire was already closed — `sw.js`'s `push` handler marks the day before the wake can ask — so a late banner is one message shown late, never a second one.
- **The reminder's two missing halves: the bills it reminds about, and the install a wake needs.** The push body was the same sentence every day, though the profile's own `settings.recurring` list says what is due — the run (`lib/reminder-run.mjs`) now appends a **bills hint**: `billsDueHint(doc, localDate)` is pure and exported (counts `nextDate <= localDate`, words `1 bill`/`2 bills`, and an unreadable document, list or date answers `''` rather than throwing), read lazily per profile from the cloud store through `cloud.mjs`'s own `CLOUD_STORE`/`keyFor`, which are **exported rather than copied** — a second guess at the key layout is a second place the hint could read the wrong document or none — and cached per profile+date in the handler. The body is the one line plus the hint, and `scripts/test-reminder-push.mjs` **section 19** pins both halves (the pure counter's edges, the source shapes, and three end-to-end deliveries through the real handler: a document with bills, a record with no profile, a profile with no document). The other half is on screen: the modal that explains the wake now offers the **install that makes a wake possible** — `installRow = canInstallApp() ? … promptInstall()`, the same captured prompt the ☰ menu's Install row shares — beside the sentence that says why, because an uninstalled tab can never run a periodic sync and “it exists three menu levels away” is how a prerequisite stays invisible. The **local** delivery needed the same sentence: `reminderCopy` — the one function the system banner and the in-app toast both read — appends a hint from a provider, `setDueBillsProvider(fn)` in `reminders.js`, which `app.js` wires once at boot as `setDueBillsProvider(() => billsDueHintFor(state.settings.recurring, today()))`. `billsDueHintFor` mirrors the sender's `billsDueHint` (same leading space, `nextDate <= today`, same pluralisation, an unreadable list answering `''`) because two counters of "what is due" are two answers, and a throwing provider costs the delivery nothing (`catch → ''`). Source-pinned in `scripts/test-integrity.mjs` section 18.
- **"Push is on" is a memory of a toggle, and the reminder it promises was being cancelled by the app's own safety net.** The reported symptom was a reminder that never fired at its set hour on an installed Android phone whose reminder modal said push was on — and it survived every previous fix because every previous fix was about a path that was working. Two independent faults, one masked the other. **(a) The wake's catch-up pre-empted the hour.** The pre-hour catch ("a record older than yesterday means a day slipped") fires and then calls `markReminderFired(day)` — and the `push` handler drops any message for a day that already has its banner, because the shared tag would only re-alert it. So an early wake did not ADD a notification: it marked the day delivered and **cancelled the 20:00 push the server was about to send**, arriving instead at whatever hour the browser woke the worker (Chrome's periodic sync is engagement- and charge-gated, so typically overnight). The fix is a field the page has always known and never told the worker: `mirrorWakeRecord()` now carries `push: s.pushSubscribed`, and `dailyReminderWake` ends on it **before the hour only** — a device with an armed subscription has its closed-app reminder delivered by the SERVER at the hour the user chose, which needs nothing awake on the phone, so the net has nothing to cover there; after the hour the wake keeps its duty, because a push is bounded (`TTL: 3600`) and a phone unreachable at its hour has nothing else left to fire it. **(b) Nothing could tell that the subscription had died.** `settings.pushSubscribed` says a subscribe once happened; it cannot say the server still holds the record (the sender prunes one the push service calls gone — `410` — which is the one delete the device never hears about) or that the subscription is bound to the key the server signs with (a changed VAPID source rebinds nothing: every push is refused `403` and counted only in the sender's log, where `sent=0` and a quiet day look identical). Both read exactly like a reminder that fires only when the app is open, and both are repaired by the same operation, so `verifyReminderPush()` in `reminders.js` now asks the live server — on every start (gated on subscribed + already-granted permission: starting the app must never be what asks for the prompt) and once per open of the modal. It re-subscribes when the browser holds no subscription, re-subscribes when `subscription.options.applicationServerKey` disagrees with the key the endpoint serves (skipped, not guessed, on a browser that does not expose `options`), and re-POSTs when the record is gone. The ask is **a probe** — `PUT { probe: true, endpoint }`, answered `200 {stored, time}` / `404` by `reminders-push.mjs` without sending anything, because the call that already existed (plain `PUT`) is Send test push and a banner on every start is not a health check. A server that cannot be reached is **not a verdict**: nothing is cleared, nothing is re-subscribed, and the status says `unreachable` — a phone in a tunnel must not have its reminder torn down. The modal reads the verdict instead of the toggle (`PUSH_VERDICT_TEXT`), so a `no-record`/`key-mismatch`/`probe-failed` state is stated as what it is and offered as **one tap** (`Re-register` = unsubscribe + subscribe + re-verify), rather than described three taps away. Pinned in `scripts/test-reminder-push.mjs`: section 18 gained three behavioral checks against the REAL `sw.js` (an armed push is never pre-empted before the hour and the day is left unmarked; the same day with `push: false` still catches up; after the hour an armed push does **not** silence the wake) and seven against the real `reminders.js` (a live subscription verified read-only, one key GET + one probe and no POST; a `404` record repaired and left switched on; a key mismatch re-subscribed with a NEW subscription; offline changing nothing; a browser-dropped subscription re-created; the mirror carrying `push` both ways), with the source pins for the yield's PLACEMENT (inside `!due`, where a due-time check would silence the path with nothing behind it), the start gate and the modal's three new shapes; and a new section 21 checks the probe against the real handler (answered, delivers nothing, `404` for a record that is not held, `401` without the password). **7/7 mutations caught** (the yield removed, the yield applied after the hour too, the mirror field dropped, offline tearing the subscription down, the probe delivering, a 404 not repaired, the key comparison inverted) — and the yield was checked live in the served app by reading the mirrored record back out of Cache Storage (`{enabled: true, push: false, time: '20:00'}`, the exact object the worker decides from). One honest limit, stated here rather than discovered later: the field means "a push is armed", not "a push is certainly alive" — a subscription that has died since the last check leaves the wake holding back for one day, which is why the verification runs at every start, and why an unverifiable device keeps its flag and its net.
- **A device that travels takes the sender with it — and the re-announce that fixes that must not become a prompt, a POST on every boot, or a verdict.** The sender aims at the zone it was **told**, and it is only told on subscribe or on a time change — so a phone that crossed a border kept receiving the push at the old zone's hour while the local scheduler used the new one: two halves of one reminder, hours apart, with nothing on screen saying which was right. `currentZone()` (Intl → `'UTC'` fallback in a try/catch, because a wrong zone is a reminder at the wrong hour and UTC is at least one a user can reason about) is now read in **exactly one place**, stored as `pushZone` on subscribe and sent as `zone` in the POST body — a second inline read at the announce would be a second answer to “what zone is this device in”, free to drift. `startReminderScheduler()` re-announces when the recorded zone disagrees, and every gate around it stops the fix being worse than the bug: **`pushSubscribed`** (an unsubscribed device has nothing to re-tell — belt-and-braces with `updateReminderPushTime`'s own skip), **`pushZone !== currentZone()`** (the agree case is *every* ordinary boot, and it must not POST), and **`notificationPermission() === 'granted'`** (starting the app must never be what asks for the prompt — not even a key fetch). The announce is `.catch(() => {})` best effort, and a **refused** announce leaves the old record in place, so the next start sees the same disagreement and retries; a backfilled zone needs no migration, because an old subscription simply has `pushZone: null` and `null !== zone`. Pinned in `scripts/test-reminder-push.mjs` (**section 17**, each scenario on its own module instance since `startReminderScheduler` is one-shot, against a fake store/push-service with `pushFetch`'s uncleared 12 s timer unref'd so exit stays fast): a subscribe stores and sends the zone, a travelled start re-announces (GET key → POST record, in that order), permission-ungranted and unsubscribed starts fetch **nothing**, an agreeing start is silent, a null zone is backfilled, a refused announce is retried on the next start — plus the source pins a behavioral run cannot see (one `resolvedOptions` in the file, `zone: currentZone()` in the body, the three-part gate, the `.catch`, the UTC fallback). **8/8 mutations caught.**
- **The on-time path runs on somebody else's clock, and that clock can stop — so the promise now expires, the job is triggerable, and the failure is visible.** (Found after "it still didn't fire at the set time" on a device whose modal said *Push is on*.) A sender that nothing calls is indistinguishable from a healthy subscription, and NOTHING here could see that: the record was stored, the key matched, the app said push was on, and no run had ever reached the device — the same symptom as a dead subscription, three layers further down. The job therefore lives in `netlify/functions/lib/reminder-run.mjs` (`runReminderTick` + `billsDueHint` + the window), reached over HTTP only, so there is one copy of the loop and one answer to "was this device already sent to today" (`check-worker-config.mjs` fails if the entry point stops calling the lib). Three repairs, pinned in `scripts/test-reminder-push.mjs` (225 checks now, sections 18 and 22 plus the source pins; **11/11 mutations caught**):
  - **The wake's deferral has an expiry.** `mirrorWakeRecord()` writes `pushAliveUntil` — `Date.now() + PUSH_TRUST_MS` (26 h) while the server is believed to be running, **0** when it is not — and `pushCoversHour(record, nowMs)` in `sw.js` requires a positive future horizon. A bare `record.push === true` is the version that shipped and the version that fails silently: the wake, the one path with nothing behind it, waits for ever for a push that is never sent. Verified live from the page: a scheduler 5 min stale mirrors a future horizon; 3 days stale, and `schedulerOk: false`, mirror 0.
  - **Every run records a heartbeat and the app reads it.** The run writes `{ ranAt, ok, error, considered, sent, pruned, warming, rejected }` to `meta:reminder-send` (deliberately outside `push:`, which is the subscription list the loop walks); the push probe returns it beside the record; `reminders.js` keeps `schedulerAt`/`schedulerOk`, `schedulerAlive()` is tri-state (ran recently / has run and is not running / never heard from) so "never asked" cannot read as a failure, and the modal says which — "last ran 2 min ago — push is being sent", "last ran 4 days ago — no closed-app push is being sent. The browser's own background reminder covers the day instead", or "ran but cannot sign a push" (the VAPID case, which is a different problem for a different person). The modal also reports the last reminder this device ACTUALLY received and by which path — `by: 'push' | 'wake' | 'page'`, written by whichever path delivered — because "did it ever fire?" had no answer anywhere before.
  - **The server's own copy of the schedule is read back, compared, and repaired** — because that copy, not the device's picker, is what decides when a push is sent. `isDue()` in the sender reads the RECORD's `time` and `zone`, so a record whose copy went stale (the hour was changed while the phone was offline and the follow-up write never landed) pushes at the OLD hour while every screen on the device reads the new one; and a zone `Intl` cannot parse makes every run answer "not due", which is **nothing sent, for ever, with no error anywhere** — the one failure where the server is healthy, the subscription is healthy, and the reminder simply never comes. The probe (`PUT { probe: true }` in `reminders-push.mjs`) has always returned `time` and returned nothing about it; it returns `zone` too now, `verifyReminderPush()` keeps the pair as an **observation** (`serverTime`/`serverZone` — a fresh probe clears `pushTimeFixedAt`, because the observation that stamp was about is gone) and, when it disagrees with the device, **rewrites the record** (`updateReminderPushTime()`, stamping `pushTimeFixedAt`) rather than describing it — one request fixes it and the modal says which happened. `reminderServerSchedule()` is the accessor: `matches` requires the same hour, the same zone **and** a zone `Intl` can actually read, and `zoneUsable` is what turns the third case into its own sentence ("a time zone it cannot read … so no scheduled push can be sent at all") instead of a silent never. The modal's line reads: the hour it is aimed at when they agree, the hour it was aimed at *instead* when they do not, and that it was rewritten just now when it was. Verified live in the served app against a seeded record: the agreeing sentence, the mismatched-hour sentence, and the unreadable-zone sentence.
  - **A banner at the wrong hour is the browser's wake, and that is now a readable fact rather than a guess.** The wake can NEVER be on time — Periodic Background Sync is the browser's own schedule (`minInterval` is a floor) and `dailyReminderWake` fires any time after the hour — so a reminder set for 08:00 that arrives at 11:30 is the wake covering a day the push did not deliver. Every push path is bounded in clock terms instead: a run fires only when something calls it, inside a `WINDOW_MINUTES = 10` window, and the message goes out with `Urgency: high` / `TTL: 3600`, so a push is sent within its hour and displayed within the hour after it — anything outside that window came from the phone, not from the server. The modal now names which path delivered the last reminder on this device (`sent by the server` / the wake / `shown while the app was open`), what the server last sent to this device, what the sender's last run MET, and the hour the server is aimed at — so "push is on and the banner is late" resolves to one of four different faults (nothing calling the sender, a refused subscription, a stale server-side hour, a wake that got there first) without a support conversation.
  - **A sender that stopped is on the DASHBOARD, not only in the reminder sheet.** The sheet words the heartbeat, but the sheet is opened by somebody who already suspects something — and the whole symptom of a dead sender is silence on the phone, so the fact has to be visible where the user actually lands. `reminderSenderAlert()` is the rule and `screenDashboard` draws it as a `role='alert'` card (the gift-card/voucher shape, swipe-dismissable) with the repair one tap away ("Reminder settings" → the sheet, where "Run server reminder now" is). The rule is the part worth knowing: **a day**, measured two ways, and both cases are only news once they are that old. `'stale'` is a heartbeat older than `SENDER_STALE_MS` — a sender nothing has called in a day, with a phone that has not been sent to — and `'never'` is a probe that answered and found no heartbeat at all, held back by the same day **measured from `pushSubscribedAt`**, because a site configured a minute ago has simply not written its first heartbeat yet (that timestamp is stamped once, on the way ON: a re-register repairs a record, it does not make the device newer to a promise it has been holding for weeks). It answers null for a reminder that is off (nothing promised), for a device with no subscription, for one nobody has checked (`schedulerChecked` false — *we have not asked* is not *they stopped*), and for anything younger than the day — including a 2.5-hour-old heartbeat, which is a stall and not what this card is for. The card re-arms when the sender comes back (the `alertDismissed` clear is guarded so the common case — no alert — costs no write, unlike the voucher notice's unconditional call), so a dismissal cannot outlive the fault it was dismissing.   - **The same job is reachable over HTTP.** `reminders-tick.mjs` runs it on `GET|POST /api/reminders-tick` (and on the pre-rename `/.netlify/functions/reminders-tick` spelling), authed by the profile's app password (header, or `?password=&profile=` for a service that can only reach a URL), throttled on failures, idempotent (a record already delivered today is not delivered again, so two triggers racing cannot double-send), answering with the run's heartbeat. `check-worker-config.mjs` requires it to stay in the Worker's route table and to keep calling `lib/reminder-run.mjs`, the only way into the job. A device that is OPEN at the hour also fires it (`triggerServerTick()` from `fire()`), so any running copy of the app is a trigger for the closed ones.
