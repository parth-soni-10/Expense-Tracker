# Project Instructions — cents. (Expense Tracker)

Local-first, single-page expense tracker. No build step, no framework — plain ES modules, hand-written CSS, hash routing. Deployable to Netlify (static files + 3 serverless functions).

## Tech Stack
- **Vanilla JS (ES modules)** — `app.js` (~9.2k lines) is the whole UI; supporting modules are `storage.js` (state persistence, validation, backup parsing, the JSON and CSV exports), `csv.js` (the one CSV field rule — quoting and the apostrophe guard against a note being read as a formula — shared by `storage.js`'s entries export and `tesco.js`'s workbook read/write), `settings.js` (device settings), `sync.js` (cloud sync client), `sync-merge.js` (cloud/local merge), `seed.js` (structural defaults), `profiles.js` (per-profile namespacing + admin policy), `reminders.js` (daily reminder + Web Push), `tour.js` (the driver.js walkthrough), `tesco.js` (the Tesco Pay screen, roster-photo reader, pixel prep pipeline and workbook import) and `tesco-pay.js` (the pay engine `tesco.js` is built on — rates, hours, tax, week/month roll-ups).
- **`tesco-pay.js` is the boot half of Tesco Pay, and that split is load-bearing**: `app.js` imports it statically (the dashboard's Tesco line needs `monthSummary`/`shiftPay`), while `tesco.js` — 240 KB of screen, OCR and import — is reached only through `import('./tesco.js')` on the first visit to `#tesco`. `scripts/check-boot-payload.mjs` pins the static closure by name and by size, so a new eager import fails the build instead of quietly costing every boot ~240 KB of parse. The screen's own nav link warms the module on pointer-over/focus, so the tab is usually already there when clicked.
- **State**: one validated JSON document in `localStorage` (`expense-tracker:v1`), schema-versioned (`schemaVersion: 2`).
- **Cloud sync**: Netlify Functions (`netlify/functions/sync.mjs`) proxy a single JSON file in a private GitHub repo; `setup-token.mjs` mints single-use setup links; `lib/` holds shared auth/token/store helpers.
- **Vendors** (in `vendor/`, fetched through `loadVendor()` on first use): SweetAlert2, flatpickr, tippy/popper, Sortable, anime + confetti, tabbable + focus-trap, Fuse.js, SheetJS — plus driver.js for the tour, and the Tesseract OCR engine under `vendor/tesseract/`, injected on the first roster scan.
- **No test framework.** Verification = `node --check` on every file + ad-hoc node scripts + live preview.

## Code Style
- Files: lowercase `kebab-case.js` / `*.mjs` for Netlify functions.
- DOM is built with the `$` helper (`app.js`) — it renders children as **text nodes** by default, so strings never need manual escaping. Prefer `$` over string `innerHTML`; all `innerHTML` assignments must stay constant/clear-only.
- State mutations funnel through `saveState`; destructive actions also write the **undo journal** (`saveUndoJournal` in `storage.js`) so toasts can offer Undo.

- **A route change renders and stops there.** `renderRoute` is the `hashchange` handler and all it does is call `render()`: the swap is deferred to the next animation frame (with a 24 ms timer as the guaranteed flush) and `_render` builds and appends the screen. **No view transition, no entrance animation** — and that is measured, not taste. The change used to be handed to the **View Transitions API**, which was the stutter, because a transition costs more than its animation: the browser will not run the update callback until it has captured the old state, and capturing needs a compositor frame, so a document that cannot produce one waited out the entire 250 ms fallback budget before drawing *anything* — measured at **~270 ms per tab switch (~250 of it the budget) against ~36 ms** with no transition at all, on top of the 180/220 ms cross-fade everywhere the API did work. `scripts/test-motion.mjs` pins the machinery **absent**: no `startViewTransition`, no `VT_BUDGET`, no deferral inside `renderRoute`, no rule that animates `.screen`, no `.stagger`, no `::view-transition` pseudos and no `riseIn`/`centsVt`/`countUp` keyframes — 6/6 mutations caught, so bringing any of it back fails the build. The animation-frame deferral and the crash boundary stay in `render()` — do not add a second render path. `lastRenderedRoute` outlived the transition it was written for: a route **change** scrolls to the top and takes the new screen's initial focus, a same-route repaint preserves both — it is `routeChanged` (not `entrance`) and it drives no animation. `screenIn` survives for things that appear *into* a screen already up (the bulk bar, an empty state), where a fade is information rather than latency.
- Charts are read through popups, and the wiring is one function for all of them: `wireChartTips(scopeEl, selector)` installs **one delegated tippy instance per scope** (`delegate` takes a single selector, and the scopes are unrelated cards — the heat map, the donut, the month-by-month chart), resolving content from `data-chart-tip` and falling back to the heat map's older `data-tip`, with `has-tippy` on the scope suppressing the CSS-only `.heat-tip`. The warm path wires the scope **before it is mounted**, which is deliberate: the listeners are bound to the element and fire once it is in the tree — so do not add an `isConnected` guard to the sync path the way the cold path has one, or every chart on a warm load silently loses its popups. A chart mark's popup is its only way to be read, since a bar is a shape and not a table cell, so a new chart either carries `data-chart-tip` **and** is covered by a `wireChartTips` call or it cannot be read at all. The month-by-month chart's targets are one transparent column per month (`.mom-hit`, `pointer-events: all`) appended *over* the bars, not a tip per bar: a bar is ~10px wide, which is not a hover target on a phone, and a month's two figures belong together in one popup. `scripts/test-motion.mjs` pins the contract that catches the silent half of this — every emitted `data-*-tip` attribute must be covered by a `wireChartTips` selector — proved with a mutation (renaming one mark's attribute fails it twice: the uncovered mark and the orphaned selector). Note what is *not* covered: tippy's trigger. The preview bridge emits no hover events at all (a trusted click produces `click` and nothing else), and a control instance fails identically to the shipped heat map, so the trigger is verified only by the fact that the configuration is the heat map's, byte for byte.
- Headline figures count when they change, through `paintFigure` in `app.js`: keyed by a stable name, tweened from the value last painted to the new one, with the **final frame writing the formatted target** so a total can never come to rest on an intermediate. A figure that did not change does not move (every keystroke repaints the screen) and one never painted before arrives at its value, so the `key` is what carries the meaning — two figures sharing one would steal each other's history. `scripts/test-motion.mjs` lifts the function's own source text out of `app.js` (which cannot be imported: it touches the DOM on evaluation) and runs it against a fake clock; add cases there, not by watching the screen.

## Data Durability
Three of these are one story — the document is the whole of the user's data — and the fourth is the reason it can be written down again at all.
- **A backup can be read back, not just written.** `Export data` had no counterpart anywhere in the app (no `FileReader`, no file input outside the Tesco importers), so the backup the quota notice tells the user to make could never be opened. `Data → Restore from backup` reads a `.json` export and **merges** it (`mergeStates`, the same union the cloud path uses): the newest version of each entry wins, tombstones still hold, and nothing on the device is deleted. `parseBackup(text)` in `storage.js` owns the rules — pure, never throws, and answers with a reason the UI words for the user (`empty` / `too-large` / `unreadable` / `not-a-backup`) plus `kept`/`dropped` counts, because a file whose entries were all junk validates to an empty document and a merge of nothing looks like a successful restore of nothing. Two things are stripped before validation and both matter: **`settings.pinHash`** (validateState MIGRATES a legacy hash into device storage when the device has no PIN, so an untrusted file would otherwise get to set this device's lock — the app's own export deletes the key, so a real backup is unaffected) and **`localResetAt`** (a whole-document tombstone that later data superseded; restoring an old copy of one would re-assert it). Both caps — 32 MB of text, 100k entries — are checked *before* the parse, so an absurd file is refused for its size rather than reported as unreadable. Pinned in `scripts/test-integrity.mjs` (“the other half of a backup: reading it back”, 10/10 mutations caught).
- **A restore is one undo step, and it reverts the whole document.** The undo closure snapshots `state` before the merge and writes it back wholesale — a merge touches settings and the Tesco tables too, so the entry-only journal is the wrong shape for it. It is therefore session-scoped, and `trackAction` with no journal data clears the reload-safe journal on purpose: that journal describes a different action.
- **The quarantine copy is reachable.** `loadState` parks a document it cannot parse instead of dropping it; the notice named a storage *key* at a user with no way to open one, and `unreadableBackup()` was exported but imported by nobody. `Data → Recover unreadable copy` appears only when such a copy exists, offers it as a merge when it parses at all, and offers the raw bytes as a download when it does not — those bytes are the only copy of that ledger.
- **A second tab is a second copy of the document, and it used to clobber.** Every tab holds the whole document in memory and every save writes ALL of it back, so the tab that writes second erases the entry the other one just added; there was no `storage` listener and no `BroadcastChannel` anywhere. Now a foreign write is merged: the tab that still holds something the writer did not writes the union back. `foreignWriteNeeded(merged, incoming)` (in `storage.js`, pure and pinned) is what stops the pair writing at each other forever — after one round trip neither side holds anything the other lacks, so nobody writes again. The document is re-read from storage rather than taken from `ev.newValue` (an event is a notification, not a snapshot, and `newValue` is null when a key is removed). Verified live with two tabs: a stale write that dropped the other tab's entry came back as the union, with zero further writes from either side.
- **The ledger is also a spreadsheet.** `Data → Export CSV` writes one row per entry (`entriesCsv` in `storage.js`, `ENTRIES_CSV_HEADER`: date, type, category, details, amount, method, note) — newest first with the History screen's own tie-breaks, the label rather than the stored id, and money at two decimals because "12.40" has to stay a cell a spreadsheet can total. The **label resolvers are handed in from `app.js`** (`categoryLabel`/`methodLabel`) instead of being re-derived in `storage.js`: a second copy of the naming rules is a second answer to "what is category `gro` called", free to drift from the one on screen — and custom categories live in the document's own `settings`. There is no importer for this file, so a column may be added without breaking a round trip. The field rule lives in **`csv.js`**, shared with `tesco.js` (which writes the workbook out and reads it back), because a rule with two implementations can disagree with itself: quoting when it has to, and an **apostrophe in front of a value a spreadsheet would read as a formula** — a note can be typed, imported from someone else's file, or arrive in a synced cloud copy, so the export is not a safe container for one. A plain number is deliberately excluded from that guard, or the apostrophe that defuses `=SUM(A1)` would turn a −56.08 refund into text. The UTF-8 BOM is added at the file boundary only (Excel on Windows reads a BOM-less UTF-8 file in the machine's ANSI code page), so the text the tests compare is what `csvDocument()` produced.
- **Durable storage is asked for once per boot** (`navigator.storage.persist()`, a no-op once granted) and the Data menu shows the document's own size and whether the browser promised to keep it (`persistent` / `best-effort`) — the ledger is the whole of the app's data, so “best-effort” is a fact the user should be able to see. The call is refused in some profiles; the readout says so rather than pretending.

## Accessibility
- **The audit is a page, and a Node guard keeps it honest.** A Node script cannot read a rendered DOM, so the sweep lives in `a11y-harness.html`: it loads the real app in a **visible**, CSS-scaled iframe and drives it through every route and every surface that *opens* — the menu and its drill-downs, and the modals they reach — never clicking inside an open modal, so the ledger it audits is untouched. The frame must stay on-screen (the app defers its render to an animation frame and a background frame is throttled, so a hidden harness audits nothing) and **every step gets a fresh frame reload**, because a modal left behind is a second scope counted against an unrelated surface. It reports four defects per surface: a control with no accessible name, two controls in one scope sharing an `aria-label`, a form field with no label at all, and an `<img>` with no `alt`. Its verdict is deliberately the **sum of all four**.
- **The audit has to run in a state a user can be in, and it must never write the ledger.** A first run covers the whole viewport with the setup overlay, and nothing in the menu is reachable behind it — so a run that drives the menu anyway audits screens no user can reach, and the overlay's own PIN fields then count as duplicates of the menu's (that is exactly how a fresh device reported "New PIN ×2"). The harness therefore walks the overlay out through **its own skip control** before auditing, folds the outcome into a run-level note (`setup overlay dismissed` / `no setup overlay`, and a stuck overlay makes the run non-clean), and reports what each skipped surface needed. It must never seed storage to get there: it is served from the app's **own origin**, so it shares the app's `localStorage` and a seeded document would overwrite the ledger the harness promises not to change. Both rules are pinned in `scripts/check-a11y.mjs` (as call sites, not names) and proved by 8/8 mutations.
- **`aria-label` is an addressed identity, not a label** — `restoreFocusedField` looks fields up by it and so does the harness, so two controls on one screen sharing one is a bug rather than a cosmetic wart. That is why the edit sheet's fields are `Edit shift …` while the Add-shift card owns `Shift …`.
- **`scripts/check-a11y.mjs` pins the harness against the app's own lists**, so the audit cannot quietly stop covering the app and report 0 problems for the part it skipped: every route in `seed.js`'s `TABS`, every level `menuDrill()` can reach, and every modal `buildMenuLevel()` opens — declared in the harness as `MODAL_OPENERS` and asserted **both ways**, so a stale claim fails as loudly as a missing one. Exactly three openers are exempt, and each is stated in the guard rather than assumed: `openRestorePicker` (the OS file dialog, which a page cannot see or dismiss), `startAppTour` (driver.js popovers live on `<body>`, outside every scope the harness reads) and `showProfilePicker` (the menu row and header chip that reach it exist only on a device with more than one profile, so a step would report “skipped” on every ordinary run — a skip has to mean “this device could not reach it”, not “this device never has it”). It also fails if the verdict stops counting any of the four defect classes, if the page stops being dev-only (`status = 404` **and** `force = true` in `netlify.toml`, plus `.netlifyignore`), or if the harness stops being named in README/CLAUDE — an audit nobody knows about is one nobody runs.
- **The one defect that actually shipped is pinned statically**: the History month chevrons were `monthNav(iconSpan('chevron-left'…), …)` with no label, and an icon span is `aria-hidden`, so they read as "button, dimmed" and nothing else. `monthNav(label, onClick, disabled, ariaLabel)` is what writes the label, and the guard fails any call whose visible label is an `iconSpan(` and which passes no fourth argument.

## Vendored UI Libraries
The vendored browser builds — twelve minified ones, two stylesheets (`flatpickr.min.css`, `driver.css`) and the Tesseract OCR engine in `vendor/tesseract/` — live in `vendor/` and are fetched through the one lazy loader (`loadVendor(name, { js, css })` in `app.js`), because CSP `script-src 'self'` forbids a CDN and there is no bundler. Each degrades gracefully when its file is missing, and `scripts/test-ui-libs.mjs` pins that they do what the app assumes.
- **SweetAlert2** — the themed `confirm()`/`swalConfirm`, falls back to native `confirm()`.
- **flatpickr** — date fields; the native `<input type="date">` works meanwhile.
- **tippy/popper** — chart popups (`wireChartTips`); popper must load before tippy.
- **Sortable** — drag-reorder lists.
- **anime** + **confetti** — the dashboard's draw-ins and the celebrate moment.
- **tabbable + focus-trap** — modal focus containment. **Order is not cosmetic**: focus-trap 8.2.2's UMD calls `t(a, e.tabbable)` and does not bundle tabbable, so tabbable must load first (`app.js`'s `syncModalFocusTrap`). `escapeDeactivates: false` keeps Escape the modal's own business — Escape does not deactivate the trap.
- **Fuse.js 6.6.2** — History search. Stay on 6.x: **7.x publishes only `.mjs`/`.cjs`, no UMD**, so it cannot be vendored. `threshold: 0.3` is measured, not chosen by feel — at 0.4 `"12.40"` also matches a €61.50 row. `ignoreLocation`, `minMatchCharLength: 2`, weights details .5 / note .25 / categoryLabel .12 / methodLabel .08 / amountText .05. A transposed word (`trian`) is not matched at any threshold.
- **SheetJS `xlsx.mini.min.js` 0.18.5** — the Tesco workbook import. It is the **mini** build: no writers, no codepage tables, no legacy `.xls` reader, which is why the accept list omits `.xls`. Dates arrive as Excel serials, not `Date`s.
- **driver.js 1.8** — the tour. Its stylesheet is light-only, so every override in `styles.css` is prefixed `html .driver-…` to beat the later-loaded vendor sheet. Two live defects are worth remembering: the per-step hook is **`step.popover.onNextClick`** (a step-level one is silently ignored, and driver's own advance then runs while the hash never changes), and a hook REPLACES driver's advance rather than preceding it, so it must call `moveNext` itself. A step's Next therefore navigates to the NEXT step's tab (navigating to its own lands one screen behind).

## Testing
- Syntax: `node --check` (copy `.js` → `.mjs` first for ESM syntax).
- Manual: `./serve.sh [port]`, then open `http://localhost:PORT/`. Default PIN to unlock is `100901` (no personal PIN set).
- Guards: `node scripts/run-guards.mjs` runs the suite `netlify.toml` declares (16 pure-Node checks, the same command CI and the deploy use — it reads the list out of the config rather than repeating it, so the two can never drift).
- Browser-only halves (a Node guard cannot read a rendered DOM or draw a canvas) ship as dev-only pages on the served app, 404'd in `netlify.toml` and listed in `.netlifyignore`: `ocr-harness.html` for the roster reader, `a11y-harness.html` for accessibility. `check-a11y.mjs` is what keeps the second one honest — see Accessibility above.
- Cloud sync + setup links only work with a deployed Netlify function or `netlify dev`.

## Build & Run
- Dev server: `./serve.sh 8080` (picks python3 → python → npx serve).
- Deploy: push to the repo; Netlify serves `publish = "."` with no build step.
- No lint, no bundler, no package.json.
- Tesco Pay workbook → the app's own import format: `python convert-tesco-csv.py "Tesco Pay.xlsx"` (standard library only, no pip installs; reads the Data *and* Summary sheets, normalises dates/times, writes the two-table CSV).

## Conventions
- Commits: concise imperative summaries ("Fix …", "Add …", "Exclude … from …"), no conventional-commit prefixes, pushed straight to `main`.
- Amounts are euros as numbers validated to 2dp (`Math.round(a*100)/100 === a`); never silently round imported money.
- Budget calculations exclude load/withdraw balance adjustments and Revolut Savings (`RS`) transactions — check existing filters before touching budget math.
- Setup links carry encrypted tokens; the endpoint whitelist + post-unlock confirm dialog are security invariants — never bypass them.
- Tesco Pay's quick entry (the **Magic entry** card) is a thin wrapper around two module-scope, harness-pinned functions in `tesco.js`: `parseShiftText` reads the line, `shiftPreviewLine` renders what will be stored. Add a case to `scripts/test-tesco.mjs` rather than checking the card by eye — a mis-read line is a mis-paid week.
- Editing a stored shift goes through the same pair of module-scope, harness-pinned pieces: `applyShiftEdit` owns the rules (the importer's own — a date, or clock times, or stated hours) and returns `{ ok, shift }` or `{ ok, field, error }`; `updateShift` in `screenTesco` commits its answer through `snapshot`/`commitTesco` so an edit is one undo step and re-sorts the row into the week its new date belongs to. The row keeps its `id` (sync unions by id) and its `createdAt`. Add rules to `applyShiftEdit` + `scripts/test-tesco.mjs`, not to the sheet.
- A booked **week off** is not a shift but a row that states hours and no clock times — the sheet's own shape, and what the magic entry already wrote for `week off 7h`. The **Week off** card is a third module-scope, harness-pinned piece beside `applyShiftEdit`: `weekOffShift(date, hours)` takes *any* day of the week and the hours of pay and answers `{ ok: true, shift }` (or `{ ok: false, field, error }`) with that row — hours, no clock times, the note `week off`. It is dated on the **week's Sunday** (`weekStartOf`), because a pay week runs Sun → Sat and the Sunday is the date that says which week the row belongs to; the card promises in `shiftPreviewLine` over `shiftPay`, so what it shows and what the week card pays are one piece of arithmetic. Dating a week off on the Sunday is only safe because of the pay rule that goes with it: `shiftPay`'s Sunday ×1.5 is a premium for *working* Sunday, so it follows the clock times — a row with hours and no times pays the card rate (7h → €101.08, not €151.62), and only a row carrying `special` itself pays the premium. Before that rule, a Sunday-dated week off was silently paid €151.62. Add rules to `weekOffShift` (+ the pay rule to `shiftPay`) and `scripts/test-tesco.mjs`, not to the card.
- `aria-label` is an addressed identity, not a label: `restoreFocusedField` looks fields up by it, and the harness probes by it. Two controls on one screen sharing one is a bug — the edit sheet's fields are `Edit shift …` precisely because the Add-shift card already owns `Shift …`.
- The roster-photo reader (`tesco.js`) is harness-pinned too, and it is the piece most likely to be broken by a local change. Keep every step pure where it can be — the geometry helpers `dedupeWords`, `pageSkew`, `columnAnchors`, `resolveColumnDates`, `ocrEstimateTilt`, `ocrAutoContrast`, `ocrSauvola`, `ocrLocalMarks`, `ocrIllumination`, `ocrRulingLines`, `rosterColumnsFromRules`, `rosterReadQuality` take plain word lists / grey buffers and are covered by `scripts/test-tesco.mjs` ("the sheet's own geometry", "the page as ink and paper", "which reading of a photo to believe"); the pixel passes (`decodePhoto`, `levelPhoto`, `turnPhoto`, `ocrRosterRow`, `ocrPageWords`, `ocrOwnerCells`, `ocrPhotoRules`) are covered by `ocr-harness.html`. The pixel layer itself lives in `ocr-pixels.js` — one copy, imported by the reader *and* by its prep worker, because a threshold with two implementations is a threshold that can disagree with itself — and it was split out of `tesco.js` with the four functions byte-for-byte the same (proved once by diffing them against `git show HEAD:tesco.js`, since `ocrStretchCanvas` needs a canvas and cannot be run in Node).
- The reader assumes the page's geometry is the *sheet's*, not the pixels': a tilted photo is levelled once (`ocrEstimateTilt` → `levelPhoto`) before any row/cell work, a sideways photo is retried after `turnPhoto` ±90°, and the 50 % strip overlap's duplicate words are collapsed by `dedupeWords` before parsing. When a date token disagrees with its column's weekday name, the weekday name wins — the day names are what `resolveColumnDates` trusts, and the week containing today is the fallback, not "the next Tuesday". The levelling search reaches ±8.5°, the same bound `pageSkew` trusts from the words: an estimator that stops at 6° reports a 7° sheet as 6° and levels it 1° wrong, which is enough to crop every cell onto the row above.
- **The strips are the cheap reading, not the deciding one.** `ocrRosterRow` offers every reading of a photo to `rosterReadQuality`, which scores it on what it actually produced (columns, the typed name on a row, dated shifts on that row, dates distinct, and a header the week could be dated from) and the reader escalates — page, then locally-thresholded page, then the photo turned a quarter turn — until one comes back *complete*, keeping the best score otherwise. A read that **merely mentions the typed name no longer ends the scan**: a read can carry the name and still put the week's shifts on the wrong days (that is exactly what a photo lit from one side does). `read.tries` on the result records what each reading scored, and the harness prints it.
- **A rung of the ladder is a batch, run on a pool of engines.** The readings a rung is made of are independent of one another — three strips, then the plain page and the thresholded page, then both quarter turns — so `ocrRosterRow` takes them together on `createOcrPool` (at most three Tesseract workers, created on demand, `ocrPoolSize(hardwareConcurrency)` cores-1 capped at 3) and feeds the results to `consider()` **in the order the one-after-another ladder reached them**. That is what keeps the change honest: the `tries` list, the `scanned` count, `pagePass` and the reading believed are the serial ladder's, and `reads=` on the harness line still counts the readings the answer rests on rather than the ones the pool had in flight. Two rules make the pool safe. Reads on ONE worker must stay sequential, because tesseract's character whitelist and page-segmentation mode are *worker* state — and the corollary is that a batched read **must name the mode it wants** (`psm: '11'` on the turns; `ocrReadCell` sets `'7'` with every cell read rather than once for the pass) instead of inheriting whatever the rung before it left there, which with several workers would depend on which one happened to be free. And each read in flight draws into a surface of its own (`ocrScratchCanvas`) — a read is `draw → stretch → toBlob → recognize`, and the two awaits in the middle are where a shared canvas starts a second draw over the first read's pixels. That is now true of both the ladder's strip and page reads (`prepEncode` draws and reads back on one, then hands the bytes to a prep worker) and the cell pass. The caller's canvas is only the on-screen preview now, so `ocrRosterRow`'s `finally` zeroes it itself, the preview the scan started from (`discardPhoto`) being the same element. Cost profile, measured pairwise on the harness's lamp scenarios: the recognize is 13–25 s of a strip read against ~1.4 s of preparing one, and it grows with how much text the engine finds, not with pixels. Three readings in flight return about 1.9× the throughput of three in turn on a shared machine — but the real gain is pipelining, the main thread preparing the next reading while the engine works on the last, which is why the badly lit photos (77 s → 52 s on `tilted-7deg-lamp`, 45 s → 23 s on `uneven-lamp`, paired and counterbalanced) gain most and a photo the strips settle gains least. The cell pass is a batch of the same kind: `ocrOwnerCells` takes the pool rather than a worker and submits the name read and every day column together — `ocrOnScratch` gives each its own surface, and the bar walks the week as the days come back — measured at 150–400 ms against 220–590 ms one at a time. That is small because a cell is a ~0.1 MP crop, but it is the tail of every successful scan and the pass that grows with the width of the week. Adding a rung means adding a batch, not a `for` loop.
- **Preparing a read is a thread of its own** (`ocr-prep-worker.js`). A read's image is drawn, binarised and PNG-encoded before the engine sees it: on a 12 MP strip that is a draw (~30 ms), a readback, a threshold (~490 ms) and an encode (~1.7 s on the reader's thread, 0.5–0.6 s in a worker — `convertToBlob` is the faster encoder), and the reader's thread was busy through 316–684 ms of it. Measured interleaved on one machine with a `MessageChannel` ping loop, which is the only honest way here: a hidden tab throttles `setTimeout` heartbeats and reports stalls that are not there. That blocking is the one part of a scan that could not overlap the engine — while a strip was being encoded the reader could not start the next reading, collect the one that finished, or repaint the bar. So the threshold and the encode run on prep workers, and the reader's thread keeps the draw and the readback that turn the canvas into bytes worth sending: **151–292 ms of longest stall, and prep 1.4–1.8 s → 0.4–0.6 s**. `ocrStretchData` (in `ocr-pixels.js`) is the function both halves call — on an `ImageData` in the worker, through `ocrStretchCanvas` on a context for the cell pass — and that split is what makes the threshold testable in Node at all (a plain buffer, no canvas). The pool is `createOcrPool` again, sized by `ocrPrepSize(cores)`: whatever cores the engine pool (`ocrPoolSize`) and the app are not using, at least one, at most `OCR_PREP_MAX` (3). `ocrStripBox`/`ocrPageBox` decide the region, the working size and the threshold's glyph window in one place, and they stay on the reader's side of the wire on purpose — every box the engine reports is mapped back through them (`kx = box.sw / box.w`), so a box computed in two places is a box that can disagree with itself. Both are pinned in `scripts/test-tesco.mjs` ("the prep workers a read's pixels are prepared on") with the job protocol: a reply is matched to its job by id (a rung asks for three strips at once and they come back in the order the engine finishes them, not the order they were sent), a job the worker could not do fails that job alone, and a worker that died — a script that would not load, a `terminate()` mid-read — fails every read waiting on it *and every read asked for afterwards*, because a scan that hangs is worse than one that fails with a reason. Nothing outlives the scan: the buffer is transferred rather than copied, the reader's scratch canvas is zeroed on every path, and `disposeOcrWorker()` now drops the prep pool beside the engine pool, so `scripts/check-image-hygiene.mjs` lints three files rather than one. Two things this design learned the hard way, both of which the harness caught and neither of which `node --check`, the guards or the app path could: **the worker may not draw the photo itself.** Handing it a cropped bitmap to draw and binarise (5 ms of reader thread) shifts 1,716 pixels of a 12 MP strip by up to three grey levels — `drawImage` resamples a source rectangle and a pre-cut image differently, and a worker's OffscreenCanvas differs from the main thread's by ±1 even from the full bitmap — and that was enough to flip `blurry` through the cell pass, which cuts its crops from the word boxes the image produces. So the reader draws and reads back, and the engine is handed the image it was always handed, byte for byte. And **`ocrStretchCanvas`/`ocrStretchData` take the 2D context (or the pixels), not the canvas**: `getImageData`/`putImageData` are context methods, and a canvas in that argument is not an error the function can report — its own `catch` returns `'stretch'` with the image untouched, so the scan still finds a row on a good photo and only the sheet lit from one side comes back as noise (the worker passed `surface` once; `clean` and `sideways-90` passed throughout, a photo whose paper is already white paying `ocrAutoContrast` nothing, while `uneven-lamp` and `tilted-7deg-lamp` failed).
- **Two binarisations, and the photo picks.** `ocrStretchCanvas(c, w, h, view)` gives the engine either a global contrast stretch (`stretch` — keeps the grey the LSTM reads, and the anti-aliased edge of a stroke) or a local Sauvola threshold (`ink` — segmentation the engine's own global Otsu gets wrong; tesseract's maintainers call theirs "rather bad quality" and it is what every layout decision is made from). `ocrIllumination` measures the photo's own light (the spread of the *paper* level between tiles, so text does not count as unevenness) and the escalation picks the view from it. A photo the reader can read never pays for the second view.
- **Rules beat names for the column boundaries.** `ocrLocalMarks` (mean − C, not Sauvola — a hairline table rule is far too faint for a glyph threshold) → `ocrRulingLines` (long contiguous runs, never ink counts) → `rosterColumnsFromRules`, which returns a grid only when it has seven columns *and* every column the words found falls inside the span that claims it, so refining the grid can straighten a crop but never move it onto another day. The name column's right edge is a rule on every ruled roster, and that is the boundary `rosterNameColumnRight` needs to be right.
- **A day column the header did not give up goes back into its own gap** (`columnAnchors`): a column's date is derived from its *position* in the row, so filling at an edge renumbers every day after it. Read at an angle with the light falling off, the header loses one day from the middle and a left-edge fill turned Tuesday's shift into Wednesday's — a whole week paid a day late, the one misread nobody notices. Only when there is no gap does the fill go to the left edge, where a phantom day is numbered *before* the week and takes no shift the day names did not already date.
- **The reader reads the paper's grammar, not the engine's.** Five rules, each pinned in `scripts/test-tesco.mjs` (`the cell's words`, `the sheet's own geometry`, `which reading of a photo to believe`) and each a way a legible photo used to be refused or, worse, mis-dated:
  - **A minute separator is a colon, a full stop or a comma**, and a typographic minus is a minus (`parseTimeCell`, `CELL_RANGE_RE`). A colon is two dots and JPEG ringing closes the gap between them, so the engine hands back `07.00-15.00` — a whole shift, thrown away over its punctuation. A plain number is excluded (`12.40` is not a time) and a three-number date is not one either.
  - **A date may name its month and print its year** — `27-Sep`, `20 September 2026`, `22-Sep-2026` — and a printed year is obeyed even when the nearest-year guess would differ, which is what makes the turn of the year safe (a roster for the week of 29 Dec, photographed on 2 Jan, dates December and not the December after next). The month-name branch only claims a middle token that really has a letter in it, or `22/09/2026` — day, "month", year — would be read as a month name and answered `null`.
  - **A title's date range is found INSIDE a phrase, not only as one** (`dateTokensIn` → `rowDateTokens`). The engine boxes a run of print as a single word, so `Week 39 22/09/2026 - 28/09/2026 Store 3021` comes back whole — and reading only whole phrases threw away the one line that says which week the sheet covers, which is also the one line big enough to survive glare. Both rules that count a header's dates go through it (the band rule in `parseRosterWords` and the date-row choice in `columnAnchors`); which dates may *anchor a column* is still judged phrase by phrase, because a column needs a position and a phrase has one.
  - **When the title's range and the grid's day names disagree, the names win** (`resolveColumnDates`). A Monday-first range printed over a Sunday-first grid is a day out, and a week dated a day late is the misread nobody catches; the series is therefore slid by whole days to the offset the day names agree with most. It is a *slide*, not a re-dating: the range still says which week, and a range more than half a week out is a different week the slide is not allowed to invent.
  - **Corroboration is measured, scored and required** (`columnDatingAgreement` → `rosterReadQuality`). The dating is one rigid series, so how many of the sheet's own day names agree with the dates they were given is the whole of the evidence behind the week: it is worth two points a name when the reader picks between readings of one photo, and `complete` demands three agreeing names (or all of a shorter run). What that replaces is `named >= 3 || dateTokens >= 3`, which accepted a header of seven names of which two agreed — a header that describes no week at all, and one the reader would then stop on. There is deliberately no "contradicted" outcome: with one name the dating can always be slid by under a week to honour it, so "no name agrees" is not a state a real grid reaches, and low agreement is what a garbled header actually produces.
- The harness photographs the two new rules too: `dot-times` (a colon read as a dot) and `title-range-one-day-out` (a range one day out of step with the grid's first column), and its `readings:` line prints `n` names present and `a` of them agreeing — the number that says whether a week was read or guessed at.
- The camera modal (`openRosterCameraNow` in `tesco.js`) owns a live `MediaStream`, and **releasing the device is a first-class action, not a side effect of closing**: `finish()` (Cancel, Escape, backdrop, Capture, a live read that found shifts) stops the tracks, and **Stop live read releases them on the spot** — the camera light must never outlive that click. `openStream()` is the single acquire/re-acquire path so the one toggle button can cycle `Start camera → Live read → Stop live read` and be re-armed after a stop. A control with no handler is invisible until you use it: the Cancel button shipped inert and trapped the camera on.
- Anything a rebuild must not throw away lives either in `settings` (durable — written through as it is typed, e.g. `tescoName` on the scan card) or in a module-scope slot beside `scanState` / `rosterAnchor` (session-scoped, e.g. the roster's first-column date). A value computed only at build time (`weekStartOf(todayIso())`) is silently reset by every render — and with it the meaning of what the user is about to save. Both of those were wrong once: the name was saved only when a read ran, so a re-render blanked it just before the read needed it, and the anchor snapped back to this week under a month-old sheet.
- `aria-label` uniqueness is worth checking at runtime, not by eye: collect `[aria-label]` across a route (and inside every `.modal-bg`) and report repeats. Two split-slice control sets and every shift row's delete button were caught that way — the delete labels now carry the shift's own date and times, like the pencil beside them.
- `render()` does not drop a modal: `stackModal()` appends to `document.body`, outside `#app`, so a modal and its listeners survive a re-render (the camera modal's `MutationObserver` is belt-and-braces for a future sweep, not the thing keeping the camera light off).
- A week's **final bank pay** is typed off a bank statement, so no formula derives it (holiday pay, a refund, a correction all make it differ from gross − tax) — and it is a *week's* figure, not a row's, which `buildPayWeeks` enforces by summing the figures it finds (a payslip's when any payslip of that week has one, otherwise the shift rows'). Writing one figure into two homes would pay it twice, so the rule is a module-scope, harness-pinned function: `weekBankWrite(shifts, payslips, carrierId, amount)` sets it on the week's **carrier row** (its first row by date — the row `tescoCsv` puts a week's figures on) *and* on the week's own payslip (the last of that week), and clears it from every other record of that week. A blank or unreadable amount clears the week (`null` = not known, and the received line hides) rather than quietly zeroing it; it is copy-on-write, so an unchanged figure hands back the same records and the cell can tell an edit from a click-through. The cell that takes it sits in the shift row's tail — `[gross][Bank][pencil][×]` as one group, which wraps whole to its own line on a phone — and it exists on the carrier row only, one per week. It commits on **change, never on input** (the same reason the week-number field beside it waits for change: `render()` rebuilds the screen and a rebuilt number field has no caret to keep), which is why `writeWeekBank` can commit through `snapshot`/`commitTesco` for one undo step. `actualFigures` shows the received figure whenever the week has one, payslip or not — it used to need a payslip, so a net typed on a row counted in the month's total with nothing on the week to say so. Add rules to `weekBankWrite` + `scripts/test-tesco.mjs`, not to the cell.
- The tax estimate is the sheet's Potential Tax formula (`simulateTax`) with **one deliberate divergence at low earnings**, pinned in `scripts/test-tesco.mjs` ("PRSI: the low-earnings rules"): **an employee on €352 a week or less is exempt from PRSI**, and above that the €12 weekly credit tapers away by one-sixth of the excess over €352.01, reaching nothing at €424, above which the charge runs straight through on every euro of the week. The sheet charged the full rate below the threshold, which over-stated a €300 week (about 20 hours at the card rate) by €12.60 — such a week owes €0 PAYE (the €76.93 credit swallows it), €0 PRSI and only the USC, so €2.54 out, which is what a payslip shows, against the €15.14 the old formula claimed. The workbook parity the harness pins (`€550.525 → 33.18 / 7.55 / 23.12 / 8.26 / 63.85 / 478.42`, and the CSV row the export writes) therefore holds for weeks **above** the threshold, and the €287 Sunday pin's label carries the difference — it is the one cached cell the app intentionally no longer reproduces. Two things are deliberately **not** modelled, both because a weekly simulation cannot see them: the **USC exemption** (total income of €13,000 or less pays none — applied per week it would zero any holiday week for a year-round worker) and the **PRSI rate change of 1 Oct 2026** (4.2% → 4.35%). `TESCO_RATE_DEFAULTS.prsiRate` stays at the workbook's 4.2% so its rows survive an export unchanged; the rates card names both rates and that field is the user's to set.
- The Tesco stats card's three figures sit on **two bases, and each label says which** — pinned in `scripts/test-tesco.mjs` ("what a month's figures mean") with a fixed `TODAY`, because one rule is about dates and a harness reading the wall clock would change its answer on 1 October. *Hours this month* is the month's own shifts, by shift date. *Anticipated (est. net)* is a **net**, and a net is weekly — the PAYE credit, the USC bands and the PRSI threshold are all per week — so `simulateTax` runs **once per pay week on the week's whole gross**, never per row (each row would take its own credit: two €500 rows of one week pay €153.84 of PAYE between them, not €46.14), and the week is placed in the month its **Sunday** falls in, the sheet's own month rule, so a week straddling a boundary is counted once and never prorated. *Received this month* is money that **landed**, so it follows the **pay date** (`payDateOf`, week start + 11, the date every week card prints) and not the week: the week of 27 Sep is paid on 8 Oct and is October's, while the week of 30 Aug was paid on 10 Sep and is September's — reading the month off the week's start moved both edges the wrong way. `receivedTotal` takes each week's money in order of authority: a typed **Final Bank Pay** (which counts whenever it is dated, because the user watched it land), else `gross − recorded tax` (the sheet's Calculated Income, a refund week's negative tax landing as money in), else the week's **simulated net** — the same "→ net €X" the week card prints. A payslip with no shift rows beside it is the one week nothing can be derived for: its tax says nothing about the gross it came out of, so only a refund is money in. The estimate is the fix for a real defect: an unrecorded worked week used to be worth **€0** (the old `w.payslips.length && w.shifts.length` guard), which is how a month with three worked weeks and one payslip added up to that one bank line while the card still called the result "received" — and it also read a refund-only week (the case this module's own header names) as €0. A week is counted only once its **pay date has arrived** (`today`, the last parameter of both `monthSummary` and `lifetimeTotals` — pass it, don't reach for a clock), so an estimate can never claim money the bank has not paid yet. Both figures are nets on both surfaces (the card and the dashboard's Tesco line).
- A figure derived from a field rides that field's **label line** (`.tesco-numfield-label`, e.g. the Sunday rate card's `= €21.66/h`), never a trailing line under its input: a line only one cell had made that cell taller than the one beside it, so the rates grid's rows were spaced 30px then 10px and — sized to its contents — that one cell came out 30px wider than its five neighbours. The grid itself is CSS `grid` with `minmax(0, 1fr)` columns (2 / 3 from 640px / 6 from 950px, the width six columns need to hold the Sunday label's own 114px), not a wrapping flex row: wrapping broke it 4+2 on a tablet and 5+1 just below where all six fit. The hint is `nowrap` so it cannot wrap the label at 320px.
- `sw.js`'s `SHELL` array is read by two guards (`check-sw-shell.mjs`, `check-boot-payload.mjs`) with a naive quoted-string scan, so **keep comments out of it** — one apostrophe pairs with a real opening quote and shreds the list (it did: “dashboard's”). Everything the app loads belongs in it, statically *or* lazily: `check-boot-payload.mjs` fails when a module the app imports is missing from the shell, which is how `/ocr-pixels.js` turned out not to be warm for a first offline visit to `#tesco`. The OCR engine itself (6 MB of wasm + traineddata) is deliberately not precached — a cold offline scan cannot work anyway.
- `render()` rebuilds the whole screen, so never call it from a field's `onInput`: app.js restores focus by aria-label but not the caret, and a rebuilt `type=number` field has no selection API at all (`selectionStart` is null), so the next digit lands at the wrong offset. Update the field's own row in place, debounce the figures around it, and paint once the caret has left the card — see `refreshDerived` / `repaintAfterPayslipEdit` in `tesco.js`.

## Security Invariants (do not regress)
- CSP in `netlify.toml` pins SHA-256 hashes of the 5 inline scripts in `index.html` — **editing any inline script requires re-hashing or the app won't boot** (browser console reports the correct hashes).
- `lib/tokens.mjs` = AES-256-GCM setup tokens, single-use via `lib/store.mjs` (Blobs, in-memory fallback). Password must never appear in URLs.
- Both functions: constant-time password compare (`lib/auth.mjs`), per-IP failure throttle, `APP_PASSWORD` ≥ 8 chars.
- **The push signing pair is resolved in exactly one place and checked before it is trusted** (`vapidConfig()` in `lib/webpush.mjs`, called by `reminders-push.mjs`'s GET and test push and by the scheduled `reminders-send.mjs`). `VAPID_PUBLIC_KEY` is served on an unauthenticated endpoint by design — a browser needs it before it can subscribe — so a pair pasted the wrong way round puts the **private seed** in public: it happened on this project's own deploy, which answered `200` with the 43-character seed as its `publicKey`, and push was broken twice over, since no browser will subscribe with 32 bytes either. So the configured pair is used only when the public half is a 65-byte `0x04` point *and* the private half derives it; otherwise the pair is **derived** from `GITHUB_TOKEN` (HKDF-SHA256, info `cents/vapid/derive/v1`, salt `cents/vapid/keys/v1`, retried until the scalar is in `[1, n-1]`), which is what makes the endpoint self-configuring on a site whose environment was never touched. Two properties are load-bearing and both are pinned: **the derivation must be deterministic and both halves must resolve through it**, because a browser binds its subscription to the key it subscribed with and a push service rejects a JWT signed by any other key — a drift between the endpoint and the sender is a silent non-delivery — and **`APP_PASSWORD` must never be key material**, since it is short, human-chosen and readable by the user while the derivation is public in this file. `scripts/test-reminder-push.mjs` covers it (0c, 13; 3/3 mutations caught), and (12) pins the dispatcher's own clock: a record in a zone ahead of UTC is due at *its* local time and its once-a-day marker is that zone's date, not UTC's.
- `sw.js` caches same-origin GETs only — never cache sync-endpoint responses.
- A restored backup can never carry credential material: `parseBackup` strips `settings.pinHash` **before** `validateState`, which MIGRATES a legacy hash into device storage when the device has no PIN — so a hostile file would otherwise get to set this device's lock. `localResetAt` is stripped for the same class of reason (an old whole-document tombstone must not be re-asserted).
- No `eval`, no `innerHTML` with interpolated user data, no `dangerouslySetInnerHTML` equivalents.
